# Правила после сжатия контекста

Прочитай **до любых действий**. Это жёсткие инварианты: не восстанавливай их по
памяти и не переоткрывай без новых данных. Доказательства — в
`docs/execution-log.md`.

## Измерения

- Primary latency — сырая разность системных часов на ENA PHC/`chrony`;
  correction всегда `0`.
- UDP probe по control ENI — только диагностика. **Никогда** не вычитать его
  поправку из DPDK latency.
- Без выбранного ENA PHC и clock bounds до/после прогон невалиден.
- Абсолютные latency разных созданий EC2/cluster epoch несопоставимы. После
  пересоздания baseline снимается заново рядом с нашим прогоном.
- Разница меньше clock uncertainty/разброса — не победа. Финальный вывод требует
  соседних чередующихся Claude ↔ наше A/B.

## Baseline и целевая матрица

- Baseline — только неизменённый Claude `c86cc26`, запущенный **нами на нашем
  стенде**. Опубликованные Claude-цифры — лишь контекст.
- Claude `N=3` на трёх наших receiver-узлах был снят при `200k` и `2M` на
  предыдущем EC2 epoch:
  `claude-c86cc26ab2e8-r200000-n3-20260828T095225Z` и
  `claude-c86cc26ab2e8-r2000000-n3-20260828T095759Z`. Они теперь только
  исторические; для текущих instance IDs `i-0ae458ff1035bf4a4`,
  `i-0106ab3bddbb31059`, `i-051ba9ebc2dfa2e68`, `i-0d857bf4b3ed11e15`
  Claude нужно снять заново рядом с DPDK. Не подменять его опубликованными
  цифрами Claude.
- `N=1` — режим итераций; итоговый `N=3` на трёх реальных receiver-узлах
  обязателен. На текущем EC2 epoch `200k/N=3` устойчиво лучше Claude. При
  `2M/N=3` строгая планка неизменённого Claude `T183334Z` —
  `55.669/62.203/81.516 мкс`; четыре запуска текущего compact DPDK дали
  максимальный отдельный `p99.9 = 76.454..86.034 мкс` и полную доставку,
  то есть практически равный хвост. Абсолютный p50 различается меньше PHC
  uncertainty и не ранжируется. Более поздние Claude `T194728Z/T195857Z`
  получили нестабильную постоянную очередь kernel UDP на receiver-1
  (`p50 341.243/204.100 мкс`), которой нет у DPDK; не выдавать эту случайную
  деградацию baseline за устойчивый размер нашего выигрыша.
- Перед выводом сверить epoch/instance IDs, topology, rate, `N`, clock method,
  package SHA, warmup и длину серии.

## Уже закрытые развилки

- Kernel UDP: ожидание `~1 мкс`/цель 3 ухудшило хвост и удалено.
- DPDK: окно до `500 нс` ради второго события полезно около PPS-предела. Это
  другой эксперимент; не смешивать с предыдущим.
- `iovec` на разрозненных SPSC-слотах проиграл копированию; без новой раскладки
  не повторять.
- Старые абсолютные A/B Wide LLQ не дали устойчивого выигрыша, но новый
  внутрисерийный контроль переоткрыл его: `224 Б` сократили относительную цену
  поместившихся BBO/Trade на `0.45–0.55 мкс`, а Book `234 Б` эффекта не получил.
  Это ещё не итоговая победа: проверить полный формат на `200k`, `2M` и `N=3`,
  включая риск половинной глубины TX-очереди.
- SPSC — сотни наносекунд, не основной сетевой интервал. Несколько sender-ов
  отложены по просьбе пользователя.
- Custom kernel не нужен: штатное `6.17.0-1020-aws`, ENA `2.17.2` с PHC.
- Пакетный DPDK `25.11.3` и фактический ENA device подтвердили аппаратные RX
  timestamps. Hardware PHC и software `CLOCK_REALTIME` хранить раздельно;
  разность допустима только после проверенного кусочно-линейного перевода по
  редким точкам калибровки, но никогда не между сырыми значениями двух шкал.

## Проверка фактического состояния

- До замера проверить установленный package SHA/бинарники; Terraform state этого
  не доказывает.
- Control ENI остаётся у Linux/SSM, отдельный data ENI принадлежит DPDK.
- После прерывания проверить команды/процессы; после локального теста — отсутствие
  оставшихся producer/sender/receiver/consumer.
- EC2 capacity может ждать десятки минут. Не сносить стенд из-за тишины без
  проверки Terraform/CloudTrail.
- После compact прочитать конец журнала, `git status`, plan/goal и последние
  manifests. Любой пересказ подтверждать артефактами до согласия с ним.
- Служебный шаг (`aws login` и т. п.) не завершает незакрытый goal.

Менять файл только по проверяемому новому факту. Перед отменой правила записать в
`execution-log.md`, чем оно опровергнуто.
