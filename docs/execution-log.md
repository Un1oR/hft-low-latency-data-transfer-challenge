# Журнал доведения решения

Документ дополняется только новыми разделами. Уже записанные результаты не
редактируются; уточнения и исправления оформляются следующей записью.

## 2026-08-27. Этап 0: исходное состояние

- Стартовый коммит: `9bc5cc1a2565` (`Update Claude baseline analysis and completion plan`).
- Рабочее дерево перед началом чистое. Локальные измерения производительности
  не запускались: текущий компьютер для них не подготовлен.
- Terraform уже создаёт четыре одинаковых benchmark-узла в одной подсети и AZ:
  первый источник и три получателя. Узлы управляются через SSM, пакет ставится
  из временного S3 bucket, есть общий TTL и сбор результата одного unicast-прогона.
- Текущий сценарий запуска использует только первый источник и первого
  получателя. Placement group, PHC/chrony, проверка погрешности часов, общий
  паспорт запуска и fan-out пока отсутствуют.
- AWS документирует `precision-time` как отдельную стратегию placement group.
  Выбранные семействa `m7i` и `m8a` поддерживаются. Для Linux рекомендуемая
  схема: ENA PHC доступен как `/dev/ptp_ena`, а `chrony` использует его как
  предпочтительный источник.
- Одного `chronyc tracking` недостаточно для полной границы ошибки: при прямом
  использовании PHC к оценке `chrony` нужно добавлять `phc_error_bound`, который
  Nitro публикует через sysfs. Поэтому паспорт каждого прогона должен сохранять
  обе величины.

Ближайший результат этапа: инфраструктура создаёт `precision-time` placement
group, bootstrap настраивает и проверяет PHC/chrony, а общий AWS-сценарий
сохраняет состояние и границу ошибки часов до и после измерения.

Источники: [Amazon Time Sync Service и ENA PHC](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/configure-ec2-ntp.html),
[полная граница ошибки PHC](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/compare-timestamps-with-clockbound.html).

## 2026-08-27. Этап 0, промежуточный результат: реализация и план миграции

- Добавлена `precision-time` placement group; все четыре benchmark-узла входят
  в неё. Terraform provider принял стратегию, `terraform validate` завершился
  успешно.
- Bootstrap настраивает стабильную ссылку `/dev/ptp_ena`, добавляет ENA PHC как
  предпочтительный источник `chrony` и отказывает в готовности узла, если PHC,
  синхронизация или `phc_error_bound` недоступны.
- Сценарий прогона сохраняет до и после нагрузки состояние часов всех четырёх
  узлов. Консервативная локальная граница складывается из `phc_error_bound`,
  абсолютной поправки системных часов и root dispersion `chrony`; начальный
  допустимый порог задаётся `AWS_RUNNER_MAX_CLOCK_ERROR_NS` и равен `10000` нс.
- Добавлен независимый двунаправленный UDP clock probe. Round trip измеряется
  часами инициатора, время ответа — часами отражателя; из двух направлений
  считаются межхостовое смещение и расхождение направлений. Probe запускается
  только в тишине до и после нагрузки.
- Паспорт запуска теперь содержит коммит, признак незакоммиченных изменений,
  SHA256 пакета, placement group, узлы, частоту, число сообщений и допустимую
  ошибку часов. Снимки и probe сохраняются рядом с результатом в S3.
- Фактический кластер найден остановленным: четыре `m8a.xlarge` и NAT находятся
  в состоянии `stopped`. Read-only план показал `9 add / 4 change / 8 destroy`:
  заменяются четыре benchmark-узла и привязанные к их ID ресурсы; сеть, NAT,
  bucket и роли сохраняются.
- Применять замену через обычный тёплый `start` небезопасно: SSM association
  рассчитан на уже зарегистрированные узлы. Для первой миграции выбран чистый
  штатный цикл `down -> up` после сборки нового пакета.

На этом шаге код probe ещё не собирался, а AWS-узлы не запускались. Следующая
запись должна содержать результат пакетной сборки, cold create и реальные
границы ошибки часов на четырёх узлах.

- Новый `.deb` собран и проверен в чистом Ubuntu 24.04-контейнере. В пакет
  вошёл `clock_probe`; SHA256 пакета:
  `15abe235df42307a3772d13cde61db533875f2ba1877821b0b521d10f4a2def9`.
  Локально выполнена только функциональная loopback-проверка probe без

- Старый остановленный стенд и его AWS-ресурсы удалены штатно; аудит после
  удаления был чистым. Первый cold create в `us-east-1a` многократно получил
  от AWS `Server.InsufficientInstanceCapacity` для `m8a.xlarge`. В Terraform
  добавлен необязательный ручной выбор AZ; автоматический перебор зон не
  добавлялся. Повтор в предложенной AWS зоне `us-east-1b` выделил все четыре
  машины за несколько минут.
- Первоначальное предположение предыдущих записей о готовом `/dev/ptp_ena` на
  выбранной Ubuntu AMI оказалось неверным. Все четыре машины вошли в
  `precision-time` placement group, но штатный ENA-драйвер ядра Ubuntu собран
  без PHC: `modinfo ena` показывает `filename: (builtin)`, параметра
  `phc_enable` и устройства `/dev/ptp*` нет. Bootstrap закономерно остановился
  и тем самым не допустил ложного подтверждения точности.
- По официальной инструкции AWS для PHC нужен ENA 2.10+ с
  `ENA_PHC_INCLUDE=1` и `phc_enable=1`. Для текущего встроенного драйвера это
  означает отдельный kernel/AMI-путь, а не безопасную динамическую подмену по
  используемому сетевому интерфейсу. Этот путь снят с критического маршрута и
  оставлен отдельным улучшением после первых измерений.
- Рабочий первый вариант использует улучшенный локальный AWS Time Sync Service,
  также предоставляемый `precision-time`-группой. На всех четырёх узлах chrony
  выбрал `169.254.169.123`, leap status был `Normal`, наблюдаемая поправка
  системных часов составляла примерно `0.8–3.3 мкс`. Консервативная локальная
  граница `|system time| + root delay / 2 + root dispersion` получилась примерно
  `85–92 мкс`; стартовый допустимый порог поэтому исправлен на `150000` нс.
- Исправлено восстановление после неудачного создания SSM association:
  отсутствие output больше не считается успешно выполненным bootstrap. На тех
  же EC2 повторно применены пакет, CPU isolation и NTP-проверка; все четыре
  узла перезагрузились и перешли в готовое состояние. Общий AWS TTL вооружён.

Следующий шаг: короткий unicast-прогон текущего решения с NTP-снимками и
двунаправленным измерением остаточного межхостового смещения до и после
нагрузки. Это покажет, пригодна ли дешёвая схема часов для первых сравнений.

Уточняющий источник: [настройка ENA PHC и требование к драйверу](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/configure-ec2-ntp.html).

## 2026-08-27. Этап 3: функциональный fan-out на трёх AWS-получателей

- `sender` теперь принимает от одного до трёх повторяющихся параметров
  `--dest`, создаёт отдельный connected UDP socket на каждый адрес и отправляет
  каждое сообщение всем получателям до освобождения ячейки исходного SPSC-кольца.
  Первым для последовательных событий циклически становится разный сокет. В
  итоге один и тот же получатель не оказывается систематически первым или
  последним, хотя это не устраняет разброс доставки конкретного события.
- Добавлены общие и покомпонентные счётчики: полностью и частично разосланные
  сообщения, число дейтаграмм и ошибки каждого адреса. Сценарий AWS принимает
  `AWS_RUNNER_RECEIVER_COUNT=1..3`, одновременно запускает нужные receiver-узлы,
  проверяет часы относительно каждого и забирает отдельный CSV с каждого узла.
- Новый `scripts/summarize-fanout.py` проверяет равенство диапазонов `seq_id`,
  пропуски, дубли и перестановки, применяет отдельную clock correction каждого
  получателя и считает распределения задержки худшего получателя и разницы
  времени доставки одного события между получателями.
- Локально выполнен только функциональный loopback smoke test: `1000` исходных
  сообщений дали ровно `3000` дейтаграмм, каждый из трёх сокетов и приёмников
  обработал `1000`, ошибок и потерь не было. Эти числа не трактуются как
  производительность локальной машины.
- Пакет собран с SHA256
  `10493f95e5ad3c59b8709e028482f070ba68e3b408a9b3f26070dcd3191f4656`.
  Первая SSM-установка получила `403` одновременно на всех узлах: association
  стартовал сразу после смены IAM policy и опередил её распространение. После
  повторного запуска тот же пакет успешно установлен на всех четырёх узлах;
  это инфраструктурная гонка доставки, а не ошибка бинарника.
- Валидный AWS-запуск `fanout-n3-20260827T165315Z`: `100000` сообщений при

## 2026-08-27. Этап 4: компактный формат и пачки, функциональная проверка

- По уточнённому решению компактный формат и упаковка выполнены одним крупным
  изменением. Промежуточную реализацию «компактно, но одно событие на пакет» не
  создаём и на AWS не прогоняем: обе оптимизации обязательны, а ближайшая цель —
  выйти на сопоставимую с baseline отправную точку.
- Уже измеренная fan-out-версия заморожена в пакете
  `spectral-task_0.1.0+git9bc5cc1a2565.dirty+sha10493f95e5ad_amd64.deb`.
  Сборщик пакетов теперь сначала вычисляет SHA256 содержимого и сохраняет каждый
  новый `.deb` под именем с коротким хешем. В исходниках остаётся только
  актуальная реализация; старые точки восстанавливаются установкой сохранённого
  пакета, а не флагами совместимости.
- Размеры `Trade / BBO / OrderBook` стали `80 / 64 / 160` байт вместо
  `192 / 192 / 576`; среднее смешанного потока — примерно `101` вместо `320`
  байт. Текстовые справочные поля заменены числовым instrument id, цены и объёмы
  хранятся только в целых тиках/лотах, длина события выводится из типа.
- BBO и стакан остаются самостоятельными снимками. Для сделок добавлены
  накопительные объём, оборот и число сделок; они учитывают и событие, которое
  producer не смог положить в заполненную очередь, поэтому следующая дошедшая
  сделка восстанавливает агрегаты после пропуска.

`spectral.wire` сохраняется.

### Что именно показал отрицательный результат `iovec`

- События последовательны логически, но их полезные байты не образуют один
  непрерывный участок памяти. Каждый элемент SPSC — отдельный выровненный
  `SequenceSlot` со служебными `sequence`, `frame_len`, промежутками выравнивания
  и буфером максимального размера. Кроме того, фактические кадры имеют разные
  размеры `64 / 80 / 160` байт.
- Поэтому прямой путь из текущей очереди требует отдельного указателя на каждый
  кадр. Одним `pointer + length` отправить пачку нельзя: в пакет попадут
  служебные поля и неиспользованные хвосты слотов. Проверенный `iovec` убирал
  копирование, но переносил сборку пачки из простого последовательного `memcpy`
  в обход множества разрозненных участков внутри ядра.
- Более сильная гипотеза на будущее — хранить в очереди уже собранные
  wire-ready дейтаграммы либо сделать непрерывное байтовое кольцо. Тогда обычный
  случай отправляется одним указателем, а переход через конец кольца — максимум
  двумя. Это отдельная переработка границы producer/sender; к ней возвращаемся
  только после сопоставимых замеров с baseline и нахождения реальной границы
  текущего socket-пути.

### Как продолжаем сравнение с baseline

- Сейчас нельзя честно сказать, что одна реализация в целом быстрее другой.
  На нашем стенде Claude измерен только при `200k событий/с`: три повтора по
  `500000` событий с одинаковым исключением прогрева. Наш socket-путь при
  `200k` пока имеет лишь одиночный короткий прогон на `100000` событий. На
  `2M` и `4M` есть наши результаты, но нет парного Claude-прогона на том же
  стенде.
- Опорные масштабы выбираем по режимам, а не произвольно: `200k` показывает
  задержку без очереди и почти без пачек; `2M` — работу насыщенного sender с
  несколькими событиями в пакете; `4M` и последующие точки ищут границу
  устойчивости. Между последней хорошей и первой плохой точкой позже добавляем
  более плотный шаг.
- Ближайший замер — Claude `N=1` при `2M событий/с` на текущем AWS-стенде.
  Существующую длинную точку Claude `200k` не повторяем без причины; вместо
  этого приводим к сопоставимой длительности и числу повторов наше решение.

  Сетевых пропусков не было. Поправка часов `-4090` нс, неопределённость
  `46901` нс.
- Сразу после него повторён наш copy-путь:
  `fanout-n1-20260827T182830Z`, `2M` событий при `2M событий/с`. Весь диапазон
  доставлен; sender обработал `2.017M событий/с` при `100%` одного ядра, собрал

- Для низкой нагрузки снят длинный наш прогон
  `fanout-n1-20260827T183252Z`: `1.5M` событий при `200k событий/с`, без потерь,

  примерно на `5-6` мкс, но самый дальний из этих перцентилей не хуже.
  Межхостовая погрешность больше этой разницы, поэтому её причину по одной E2E

сопоставим. Следующая оптимизация должна объяснять серии, а не уменьшать ещё на
несколько наносекунд SPSC.

### Гипотеза адаптивного уплотнения пачек

- Текущее opportunistic batching уже не ждёт: оно забирает все готовые кадры и
  отправляет их сразу. При `2M` быстрый sender часто догоняет producer, поэтому
  средняя пачка остаётся `2.3`, а частота пакетов доходит примерно до
  `867k/с` — рядом с наблюдавшейся у baseline границей ENA по packet rate.
- Ждать полного MTU не нужно. Проверяем ограниченное микроожидание: целевой
  размер вычисляется примерно как `ceil(оценённая частота событий /
  безопасная частота пакетов)`, но ожидание заканчивается не позже небольшого
  бюджета, например `1-2` мкс. На `2M` это ориентировочно пачка из трёх
  событий; первый кадр ждёт до `1` мкс, средняя добавка около `0.5` мкс.
- На `200k` такой режим обязан выбирать размер `1` и отправлять немедленно.
  Без этого ожидание второго события добавило бы первому до `5` мкс и ухудшило
  именно те `p50/p99`, где мы уже немного проигрываем. Ожидание только числа
  событий без крайнего срока запрещено: неполная последняя пачка может
  зависнуть навсегда.
- Адаптацию включаем с гистерезисом только при высокой оценённой event/packet
  rate. Выигрыш — меньше системных вызовов и UDP-пакетов, потенциально более
  ровный хвост и более высокая граница нагрузки. Цена — ограниченная добавка к
  задержке первого события пачки, более сложное поведение при резкой смене
  нагрузки и риск не получить выигрыша, если серии возникают не на packet-rate
  участке.

Перед изменением batching делаем один диагностический режим: измеряем очередь
до sender, время `sender -> recv`, локальный участок после `recv` и ENA-счётчики
до/после. Затем A/B адаптивного ожидания на `200k`, `2M` и около найденной
границы покажет, сохранился ли малонагруженный путь и действительно ли сузился
хвост. Если серии находятся не на сетевом участке, эту гипотезу не развиваем.

### Уточнение гипотезы о скорости SPSC

- По имеющимся E2E-замерам нельзя утверждать, что наш sender быстрее выбирает
  очередь. Это пока объяснение-кандидат, а не измеренный результат: метки участка
  `publish -> acquire` в текущем AWS-прогоне отсутствуют.
- Конкретное преимущество нашего пути — меньше промежуточных копирований.
  Producer получает `reserve()` и строит событие сразу в слоте SHM; sender через
  `acquire()` получает неизменяемый указатель на тот же слот и копирует событие
  только один раз, сразу в непрерывную дейтаграмму. В baseline producer сначала
  копирует временное событие в source ring, а sender копирует его из ring во
  временный буфер и затем ещё раз в дейтаграмму.
- Это не бесплатное преимущество. Наш `SequenceSlot` занимает `256` байт против
  `192` байт у компактного baseline-slot; `commit()` выполняет release-запись
  поколения слота и обновляет `read_index`. У baseline меньше метаданных, но его
  snapshot-чтение копирует payload, перепроверяет публикацию и при перезаписи
  может повторять чтение; кроме того, этот протокол содержит уже описанную гонку.
- Baseline при `200k` измерил весь участок входной очереди и sender всего в
  `292-305` нс. Поэтому устранение двух копий не объясняет само по себе разницу
  E2E в несколько или десятки микросекунд. Оно может стать важным у насыщения,
  когда влияет на накопление очереди и момент формирования пачки, но это надо
  увидеть непосредственно в поэтапных метках.
- Возможная связь с худшим хвостом двухступенчатая: более быстрое догоняние
  producer оставляет меньше готовых событий в момент отправки, уменьшает пачку и
  увеличивает число UDP-пакетов. В нашем прогретом запуске `2M` было `2.307`
  события/пакет и около `867k` пакетов/с; baseline в своём основном проходе
  сообщал `2.53` и `791k` пакетов/с. Это согласуется с гипотезой о packet-rate
  нагрузке на kernel/ENA, но ещё не доказывает её.
- Отдельно уже установлен измерительный эффект: baseline явно прогревается, а
  наш runner пока сохраняет старт процесса. Это объясняет огромный начальный
  хвост нашего полного `2M`-прогона, но не оставшиеся после прогрева серии.

Следовательно, оптимизировать саму SPSC сейчас рано. Сначала добавляем метку
публикации/выбора события, распределение размеров пачки и сетевые счётчики. Они
разделят три варианта: sender действительно отстаёт, sender слишком быстро
догоняет producer и создаёт лишние пакеты либо серии появляются уже после
`send()`.

### Первый повторный чекпоинт: явный прогрев

- Перед следующей оптимизацией устраняем различие методик. Все процессы нашего
  пути запускаются один раз; первые две секунды трафика проходят producer,
  sender, сеть, receiver и consumer, но consumer не включает их в CSV. Затем
  измерение продолжается без перезапуска процессов.
- Граница задаётся не независимым таймером принимающего узла, а номером события:
  `warmup_events = ceil(rate * warmup_ms / 1000)`. Это гарантирует полный объём
  прогрева даже при разной скорости запуска SSM-команд. Значения прогрева и
  первый измеряемый `seq_id` сохраняются в manifest.
- У baseline заявленный `sleep 2` начинается на receiver до гарантированного
  старта source. В свежем `2M`-прогоне первый сохранённый повтор начался около
  `seq_id=602651`, то есть фактический прогрев трафиком был заметно короче двух
  секунд. Сотен тысяч событий, вероятно, уже достаточно, но эту особенность
  учитываем при интерпретации статических baseline-цифр.
- После функциональной проверки повторяем `N=1` на `200k` и `2M` не менее трёх
  раз. Сравниваем не только объединённые перцентили, но и разброс запусков и
  временные серии хвоста.

Развилка после чекпоинта: если обычная часть распределения отличается не больше
межзапускного разброса и погрешности часов, прекращаем разбирать baseline и
переходим к улучшению packet rate и хвоста. Если разница сохраняется устойчиво,
добавляем поэтапные метки и сначала локализуем её между SPSC, sender, сетью и
receiver; оптимизацию без такой локализации не начинаем.

### Инцидент жизненного цикла AWS-стенда

- Команда `update` была запущена после истечения TTL. Terraform state всё ещё
  содержал включённые SSM associations и уже прошедшее время удаления, тогда как
  EC2 и NAT были удалены внешним Scheduler. Terraform восстановил отсутствующие
  ресурсы, но одновременно восстановил Scheduler со старым временем, и новые
  узлы сразу же были удалены.
- После продления TTL EC2 были восстановлены. Первая попытка bootstrap не попала
  в один узел: ресурс EC2 уже существовал, но SSM Agent ещё не зарегистрировал
  машину. Повторный запуск той же association после готовности SSM завершился
  успешно.
- Это не гонка потоков и не следствие разделения ресурсов между разными
  Terraform state: все ресурсы принадлежат одному state. Нужна поэтапность между
  состояниями «EC2 создан API» и «гостевая ОС доступна через SSM». Ошибка в том,
  что `update` предполагал живой стенд и не переводил протухший стенд через те же
  фазы, что холодный `up`.
- Исправление: `update` сначала классифицирует стенд. Для живого и готового
  стенда остаётся короткое обновление пакета. Для протухшего или частично
  удалённого стенда команда обязана либо явно отказать с указанием запустить
  восстановление, либо сама повторить холодные фазы: новое будущее TTL, EC2,
  ожидание SSM, bootstrap и лишь затем включение удаления. Простое увеличение
  паузы не исправляет старый Scheduler и не является решением.

- Добавлен диагностический режим, который без изменения wire-формата сохраняет
  для каждого события время отправки дейтаграммы, возврата `recvfrom` и чтения
  consumer. В обычном режиме эти метки не записываются.
- В хорошем диагностическом запуске `fanout-n1-20260827T202007Z` на `2M`
  сырые `p50/p99/p99.9/p99.99 = 33.4/42.2/56.3/84.2` мкс. Редкий максимум
  около `99` мкс разделился между паузой до отправки (`55.5` мкс) и паузой
  после приёма (`58.9` мкс); это подтверждает, что инструмент видит разные
  источники выбросов.
- В плохом запуске `fanout-n1-20260827T202425Z` сырые значения составили
  `42.2/60.3/248.3/299.7` мкс. `p99.9` этапов: до отправки `6.4` мкс,
  от метки отправки до возврата `recvfrom` `229.6` мкс, от `recvfrom` до
  consumer `2.3` мкс. Для всех `500k` событий сумма этапов точно совпала с E2E.
- Следовательно, основной плохой хвост находится между началом системной
  отправки и возвратом системного приёма. Очередь `receiver -> consumer` и SPSC
  не являются текущим узким местом. Без аппаратных меток этот интервал пока не
  делится на kernel sender, ENA/AWS network и kernel receiver.

- Три запуска `fanout-n1-20260827T203424Z`,
  `fanout-n1-20260827T203933Z` и `fanout-n1-20260827T204417Z` дали сырые
  `p99.9 = 197.3/230.4/328.8` мкс и
  `p99.99 = 281.6/408.5/456.3` мкс. Уменьшение PPS не вылечило хвост; два из
  трёх повторов оказались хуже диапазона обычных запусков.
- Контроль `fanout-n1-20260827T204812Z` на `200k` автоматически не ждал пачку

- Вывод: гипотеза «проблема определяется только числом UDP-пакетов» отвергнута.

  batching: в дейтаграмму попадают все уже готовые события, но sender никогда
  не задерживает первое событие ради наполнения пакета.

Следующий основной шаг — DPDK с тем же компактным wire-протоколом и без
ожидания пачки. Диагностические метки сохраняем для сопоставимого разбиения UDP
и DPDK; SPSC до такого сравнения больше не оптимизируем.

### Воспроизводимая подготовка AWS-стенда к DPDK

- Terraform добавляет каждому benchmark-узлу отдельный data ENI. Основной ENI
  остаётся под Linux-драйвером `ena` и обслуживает default route и SSM; только
  второй интерфейс передаётся DPDK. На текущем стенде это PCI `27:00.0` и
  `28:00.0` соответственно.
- Ручная предварительная проверка `testpmd -> testpmd` пройдена после
  исправления порядка запуска: receiver получил `89705` пакетов, source
  отправил через ENA PMD `89704`. Предыдущая нулевая статистика была ошибкой
  оркестрации: команды `start/stop` попадали в медленную инициализацию
  `testpmd`, а не свидетельствовали о неработающем DPDK RX.
- Подготовка вынесена в идемпотентный `dpdk-prepare.sh`: устанавливаются
  Ubuntu DPDK `23.11.4-0ubuntu0.24.04.2` и `dpdk-kmods-dkms`, выделяются
  `512 x 2 MiB` hugepages, `igb_uio` загружается с `wc_activate=1`, а data ENI
  автоматически находится по PCI class и привязывается к нему. PCI-адреса и
  MAC не зашиты в скрипт.
- Подготовка встроена в Terraform bootstrap и доступна отдельно командами
  `make aws-cluster-dpdk-prepare`, `make aws-cluster-dpdk-verify` и общей
  `make aws-cluster-dpdk-ready`. Встроенный self-test на текущем стенде прошёл:
  `source_tx=91000`, `receiver_rx=90253`. `txonly` здесь намеренно упирается в
  AWS PPS allowance, поэтому это только функциональная проверка, не измерение
  производительности и не оценка потерь.
- Один из изначально чистых receiver-узлов перезагружен. После reboot SSM
  вернулся, `spectral-dpdk-bind.service` был `enabled/active`, data ENI снова
  оказался на `igb_uio`, сохранились `512` hugepages и mount
  `/dev/hugepages`. Следовательно, текущая DPDK-ready конфигурация переживает
  reboot и не зависит от ручного состояния сессии.
- Этот этап ещё не включает наш DPDK backend и ENA PHC. Следующий системный
  шаг — точечная пересборка Ubuntu `linux-aws-6.17` с ENA как модулем, установка
  официального ENA с PHC и парный socket A/B до раскатки ядра на весь стенд.

### Штатное AWS-ядро и точное время ENA PHC

- Предыдущая гипотеза о собственной пересборке ядра больше не актуальна.
  В штатном Ubuntu-пакете `linux-aws` версии `6.17.0-1020.20~24.04.1+1`
  конфигурация снова содержит `CONFIG_ENA_ETHERNET=m` и
  `CONFIG_PTP_1588_CLOCK=y`. Поэтому на стенд установлен обычный
  `6.17.0-1020-aws`, а не наше производное ядро. Это сохраняет остальные
  настройки и исправления Ubuntu AWS kernel и изолирует наше изменение до
  официального внешнего модуля ENA.
- На одном receiver сначала проверен полный путь отдельно. Официальный ENA
  `2.17.2` собран DKMS с `ENA_PHC_INCLUDE=1`, загружен с `phc_enable=1` и создал
  `/dev/ptp_ena` с именем часов `ena-ptp-00`. `chrony` выбрал эти аппаратные
  часы основным источником; локальный AWS NTP остался резервным. Второй ENI
  после reboot сохранил привязку к `igb_uio`.
- После успешной проверки тот же путь раскатан на source и три receiver-узла.
  Все они загрузили ровно `6.17.0-1020-aws`; Terraform bootstrap завершился со
  статусом `Success`. Повторная проверка дала аппаратную границу ошибки PHC
  `24.2/27.0/24.9/27.9` мкс по четырём узлам при лимите `150` мкс.
- Проверка времени теперь является обязательной частью запуска. Snapshot
  складывает текущую оценку `chrony` и экспортируемый ENA
  `phc_error_bound`; запуск отклоняется, если `chrony` не выбрал ENA PHC или
  суммарная граница превышает лимит. Обычный вызов NTP перед тестом больше не
  считается достаточным подтверждением межхостовой шкалы времени.
- DPDK не пострадал от смены ядра. После раскатки повторный функциональный
  `testpmd -> testpmd` прошёл: source и receiver показали ненулевой обмен
  (`source_tx=89610`, `receiver_rx=90268`); расхождение счётчиков связано с
  разными моментами снятия статистики, поэтому этот тест по-прежнему не
  используется как измерение потерь.
- Воспроизводимый путь теперь входит в Terraform и Make:
  `make aws-cluster-phc-ready` устанавливает штатное ядро, собирает ENA,
  выполняет нужные reboot и проверяет часы; холодный bootstrap выполняет те же
  шаги до подготовки DPDK и установки приложения.

Следующий чекпоинт — контрольные socket-запуски на `200k` и `2M событий/с` с
обязательным PHC. Они одновременно проверят, не изменило ли штатное ядро
распределение задержки, и дадут первую межхостовую метрику с достаточно узкой
явно сохранённой границей ошибки.

### Новый парный socket-чекпоинт на ENA PHC

- Первое измерение выявило методическую ошибку старого конверта: двусторонний

  `fanout-n1-20260827T222518Z` доставил `500k` измеряемых событий без потерь и

  `7326eab48bc715ed0b3312a16f5dd129f218bfb5ac07dcde070801cafd452c34`

### DPDK steady-state после исправления старта и раскатки

- Первая реализация `send_many` действительно подняла локальную скорость
  sender до `~22 млн событий/с`, но короткие запуски на `2M` теряли около
  `73%` измеряемого диапазона. Sender отдавал примерно `22.5k` дейтаграмм за
  `13.7` мс, а receiver принимал только `~7k`; стандартные и ENA allowance
  counters оставались нулевыми.
- Причина оказалась не в пропускной способности steady-state. Producer
  вычислял начальный deadline до `--wait-for-reader`. Пока DPDK открывал порт,
  этот deadline устаревал, после READY producer пытался мгновенно «догнать»
  пропущенное время, а sender выпускал накопленную очередь микровсплеском.
  Pacing теперь начинается после готовности reader.
- Сначала исправление не повлияло на AWS-цифры. Побайтовая проверка обнаружила,
  что на source оставался старый `producer`: Terraform уже ссылался на новый
  SHA пакета, но первый bootstrap association упал на известной гонке IAM/S3,
  а повторный `update` проверял только наличие установленного пакета.
  Сборка теперь включает отпечаток исходников в Debian version, bootstrap
  сохраняет SHA реально установленного пакета, readiness сверяет его с
  Terraform, а повторный `update` того же SHA заново запускает идемпотентный
  association. Для пакета `c8d00d344ee7...` локальный и удалённый SHA
  `producer` совпали (`e8a8fb0adf13...`).
- После подтверждённой установки прогон
  `fanout-dpdk-n1-20260828T001325Z` передал все `300k` событий, включая
  прогрев, без дыр, перестановок и ошибок ENA. Sender выдержал ровно
  `1,999,865 событий/с`; receiver получил все `289,939` дейтаграмм. Средняя
  наполненность была всего `1.035 события/дейтаграмму`, поэтому результат не
  опирается на скрытое ожидание пачки.
- На измеряемых `100k` событиях получены
  `p50/p99/p99.9/p99.99 = 34.5/39.9/44.8/50.0` мкс. Короткий запуск уже лучше
  новой планки Claude на `2M` (`42.3/49.0/67.8/107.9` мкс) по целевым `p50` и
  `p99.9`, но доказательство стабильности требует трёх длинных повторов.

Следующий чекпоинт — контрольные серии на `200k` и `2M` с полным прогревом и
`500k` измеряемых событий. Только после них решаем, нужна ли дополнительная
пакетизация или текущий прямой DPDK-путь уже достаточно близок к доступному
сетевому пределу.

Claude по `p50` и `p99.9` на `200k` и `2M`. Дальше нужен короткий срез частот,
чтобы найти колено задержки и первую реальную потерю, а не оптимизировать уже
выигрывающую точку вслепую.

### Первое колено нагрузки DPDK

- Для `m8a.xlarge` AWS сообщает базовую сетевую полосу `1.875 Гбит/с` и
  кратковременный максимум `12.5 Гбит/с`. На `2M` наш поток почти из одного
  события на дейтаграмму уже передаёт около `2.1 Гбит/с` только полезных байтов,
  поэтому следующим пределом заранее мог оказаться ENA, а не одно ядро sender.
- Короткий срез с прогревом локализовал резкий предел текущего opportunistic
  batching. На `2.25M` доставлены все `2.55 млн` событий, все allowance-счётчики
  нулевые, `1.044 события/дейтаграмму`, `p50/p99.9 = 27.485/44.038` мкс.
- Уже на `2.375M` ENA отметил `538885` пакетов в
  `pps_allowance_exceeded`; хотя все события дошли, `p50/p99.9` скачнули до
  `483.800/496.667` мкс. На `2.5M` было `643707` таких пакетов и потеряна одна
  дейтаграмма, на `3M` — `671861` и две дейтаграммы. Задержка в обеих верхних
  точках также около `0.48` мс.
- Значит текущая низколатентная граница находится между `2.25M` и `2.375M`
  событий/с и определяется ограничением PPS ENA. Sender при этом удерживает
  заданную скорость, producer и SPSC ничего не теряют; при росте входа
  opportunistic batching сам увеличивается до `1.35 события/дейтаграмму`, но
  слишком поздно и недостаточно, чтобы избежать ограничения.
- В `2.375M` sender после печати полной статистики один раз завершился с
  `SIGSEGV` в потоке `dpdk-intr` библиотеки ENA. Это гонка остановки из Ubuntu
  DPDK `23.11.4`: его ENA PMD освобождает очереди до несинхронного снятия
  interrupt callback; в актуальном upstream порядок обратный и снятие
  синхронное. Для нашего одноразового процесса проблемный `dev_close` временно
  не вызывается: datapath останавливается, остальные ресурсы забирает ОС при
  выходе. На измерение до остановки эта гонка не влияет.

Следующий эксперимент адресует найденный предел напрямую: после получения
одного события разрешить sender не более `500 нс` ждать второе. Если второе уже
доступно, ожидания нет; если поток редкий, верхняя цена ограничена `500 нс`.
Режим параметризован и выключен по умолчанию, чтобы сравнивать его с текущим
поведением на одинаковых бинарниках.

### Ограниченное ожидание второго события

- Sender получил параметр `--batch-wait-ns`. При ненулевом значении он после
  первого события ждёт только до заданного срока появления второго, затем
  немедленно отправляет всё уже доступное. По умолчанию ожидание выключено;
  оркестратор передаёт значение через `AWS_RUNNER_BATCH_WAIT_NS` и сохраняет
  его в манифесте запуска.
- Пакет `b305612e449d2bad1a608e38f03664b068f8a27170706f40774fcbb03adf1100`
  с режимом `500 нс` установлен на всех четырёх узлах через штатный
  `aws-cluster-update`; локальный и удалённые маркеры SHA совпали.
- На `2.375M`, где режим без ожидания уже попадал под PPS-ограничение, новый
  запуск `fanout-dpdk-n1-20260828T010100Z` доставил все `2.675 млн` событий,
  собрал в среднем `2.036 события/дейтаграмму` и дал
  `p50/p99/p99.9/p99.99 = 26.223/31.070/44.063/52.002` мкс. Все ENA allowance
  counters остались нулевыми.
- На `3M` запуск `fanout-dpdk-n1-20260828T010246Z` также прошёл без потерь и
  ограничений ENA: `2.053 события/дейтаграмму`,
  `30.353/34.396/39.472/53.723` мкс. Таким образом, ожидание второго события
  действительно убирает найденный PPS-предел, а не маскирует потери.
- Длинный контроль на `2M` (`fanout-dpdk-n1-20260828T010434Z`) доставил все
  `4.5 млн` событий и дал `33.373/37.228/45.571/66.016` мкс при
  `2.027 события/дейтаграмму`. Относительно медианы режима без ожидания это
  на `1.402` мкс хуже по `p50`, но на `10.399` мкс лучше по `p99.9`; одного
  запуска недостаточно, чтобы отделить эффект кода от смещения часов.
- На `200k` пачки ожидаемо не уплотняются. Первый запуск с `500 нс` дал
  `30.845/34.096/40.169/53.725` мкс, но соседний контроль без ожидания —
  `27.701/30.950/36.095/49.322`, а следующий запуск с ожиданием —
  `27.786/31.747/37.049/61.625`. В близкой паре цена режима по `p50` всего
  `0.085` мкс, по `p99.9` — `0.954` мкс. Первый выброс был общим смещением
  межхостовых часов, а не воспроизводимой ценой ожидания.

Результат: ограниченные `500 нс` дают полезный адаптивный режим. На редком
потоке отправка почти не меняется, на частом поток сам уплотняется примерно
вдвое и избегает ограничения пакетов в секунду. Режим пока оставлен явным
параметром, а не новым безусловным значением по умолчанию.

### Граница одного потока после уплотнения

- С `500 нс` низкая задержка сохраняется существенно дальше прежних
  `2.25M`. На `4M` (`fanout-dpdk-n1-20260828T011228Z`) доставлены все
  `4.3 млн` событий, `2.077 события/дейтаграмму`,
  `p50/p99/p99.9/p99.99 = 28.431/32.843/38.222/43.500` мкс. На `4.5M`
  (`fanout-dpdk-n1-20260828T011646Z`) — все `4.8 млн`,
  `2.316 события/дейтаграмму` и `31.258/36.224/43.121/57.745` мкс.
- На `4.75M` (`fanout-dpdk-n1-20260828T011849Z`) все события ещё дошли, но
  `p50/p99.9` скачнули до `539.981/550.729` мкс. На `5M`
  (`fanout-dpdk-n1-20260828T011416Z`) получены похожие
  `655.113/672.564` мкс. Ошибок, потерь и PPS-превышений в этих запусках нет:
  задержку создаёт очередь перед ограничителем полосы.
- Расчёт из фактических счётчиков подтверждает границу. На `4.75M` sender
  передал `577520560` байт UDP payload в `2055852` Ethernet-кадрах за
  `1.060501469` с. С добавлением `42` байт Ethernet/IP/UDP-заголовков это
  `5.008 Гбит/с`. На `5M` тем же расчётом получается `5.009 Гбит/с`, тогда
  как быстрый `4.5M` использует `4.803 Гбит/с`.
- Следовательно, новое колено находится между `4.5M` и `4.75M` событий/с и
  определяется известным лимитом AWS в `5 Гбит/с` для одного 5-tuple вне
  cluster placement group. Наш placement group имеет стратегию
  `precision-time`, а не `cluster`; постоянные `100% CPU` sender здесь не
  диагностичны, потому что DPDK-поток в любом режиме активно опрашивает
  очереди.

Теперь физическая картина для `N=1` ясна: без ожидания первым срабатывает
лимит PPS около `2.3M`, а ограниченное ожидание переносит границу до полезной
полосы одного UDP-потока около `4.6M`. Дальше проверяем, как эта схема ведёт
себя в обязательной рассылке на три получателя.

### Рассылка DPDK на два и три получателя

- Первый `N=3, 200k` запуск `fanout-dpdk-n3-20260828T012130Z` функционально
  чист: каждый получатель принял все `500k` событий, включая прогрев, а
  измеряемые диапазоны из `300k` событий полностью совпали. На этой частоте
  получается ровно одно событие в дейтаграмме и суммарно около `600k`
  пакетов/с; ограничения ENA нулевые.
- Порядок первого адресата уже циклически меняется для каждой готовой пачки.
  На первых двух получателях `p50/p99.9 = 29.554/38.538` и

предела PPS, и показываем её цену по задержке на редком потоке отдельно.

### Новая доверенная планка Claude на точных часах

- Старые сохранённые цифры Claude больше не считаются текущей планкой. Даже при
  действующем ENA PHC абсолютная односторонняя задержка заметно сдвигалась у
  обеих реализаций вместе: например, свежая медиана Claude на `200k` выросла
  примерно с `29` до `39` мкс. Локальная граница ошибки PHC подтверждает
  исправность часов, но не даёт достаточно точной поправки межхостового
  смещения для доказательства разницы меньше микросекунды.
- Поэтому основной способ сравнения теперь — соседние по времени серии на тех
  же source и receiver с проверкой часов до и после каждого запуска. Оставшийся
  TTL перед обычным запуском проверяется заранее: Terraform продлевает его
  только когда времени не хватает на сам тест и десятиминутный запас. Это убрало
  лишнюю минутную паузу между Claude и следующим DPDK-прогоном, не ослабляя
  автоматическое выключение стенда.
- Неизменяемый Claude baseline по-прежнему взят из коммита
  `c86cc26ab2e84996137f922cf175d33e9a622c29`, пакет имеет SHA256
  `7326eab48bc715ed0b3312a16f5dd129f218bfb5ac07dcde070801cafd452c34`.
  На `200k` запуск
  `claude-c86cc26ab2e8-r200000-n1-20260828T024137Z` дал медианы трёх повторов
  `p50/p99/p99.9/p99.99 = 39.086/43.779/50.120/120.985` мкс. Граница ошибки
  пары часов — `70.187` мкс.
- На `2M` новый запуск

### Прямая сборка DPDK-пакета и повторная планка Claude

- В пакете

  только после копирования для всех адресатов, поэтому время жизни указателей

### Подготовка проверки расширенного LLQ

- Собран и полностью проверен пакет
  `33097af188e4b96fff9b1ba971fec258ff197ec06ccc2029db17bea8008b2271`.
  Он передаёт ENA PMD параметр `large_llq_hdr=1` и печатает фактически
  согласованную глубину RX/TX-очередей. По документации AWS и ENA PMD режим
  увеличивает помещаемую в LLQ часть пакета с `96` до `224` байт, ценой
  уменьшения TX-очереди на старых поколениях Nitro. На наших чистых режимах
  `200k` и `2M` очередь до сих пор не переполнялась, поэтому это разумный
  обмен глубины на задержку.
- Первый запуск `fanout-dpdk-n1-20260828T033529Z` кандидату не засчитан.
  В логах отсутствовала новая строка о wide LLQ: узлы исполнили предыдущий
  пакет `5568a26c...`. Причина — добавленный ранее быстрый путь проверял только
  достаточный TTL и пропускал Terraform даже при новом
  `AWS_RUNNER_PACKAGE`.
- `ensure_run_ttl` исправлен: перед быстрым путём он считает SHA256
  запрошенного пакета и сравнивает его с `package_sha256` из Terraform state.
  При различии вызывается штатный `update`, который устанавливает пакет и
  одновременно обновляет защитное окно TTL. `bash -n` и `git diff --check`
  прошли. Повторное развёртывание остановилось до изменений AWS из-за
  истёкшей пользовательской сессии; измерение продолжится только после
  подтверждённой повторной авторизации.

- Их оценочный предел последовательного unicast для `N=3` равен примерно
  `1.68M событий/с`: около `840k пакетов/с` на source и около шести событий в

  способности наш DPDK уже выше оценочного предела Claude примерно на `19%`,
  несмотря на менее плотные пачки. По абсолютной задержке такого заявления
  не делаем из-за разных топологии, железа и межхостовых шкал времени.
- Отсюда сохраняется прежняя методика: `N=1` — быстрый режим микроитераций над
  backend-ом; `N=3` — обязательная проверка, что результат переносится на
  целевую рассылку и не упирается в TX/PPS. Отдельный новый Claude `N=3`
  адаптер в текущий runner не нужен.
- До перечитывания журнала был запущен лишний, но валидный как диагностика
  `fanout-dpdk-n3-20260828T093416Z` на `200k`. Все три измеряемых диапазона
  `400001..900000` доставлены полностью, source отправил около `600k`
  пакетов/с, ошибки отправки и allowance-счётчики ENA нулевые. Сырые медианы
  трёх узлов `12.459/80.884/57.119` мкс снова показывают почти постоянные
  межхостовые сдвиги внутри PHC-границ `64.558/75.962/67.885` мкс, поэтому
  `worst receiver` этого запуска не является чистой сетевой величиной.
  Дополнительно внутренние datagram-счётчики увидели `75` поздних номеров на
  втором узле и один скачок на `59` номеров с `70` поздними номерами на
  третьем; event-level диапазоны при этом полны и упорядочены. Аномалия
  сохранена для отдельной проверки и не трактуется как потеря доставки.
- На source-узле через `testpmd` проверены реальные возможности используемого
  `net_ena` из DPDK 23.11. RX поддерживает только проверки контрольных сумм и
  scatter, TX — контрольные суммы и multi-segment; timestamp offload не
  объявлен ни в одном направлении. Поэтому аппаратную RX-метку kernel ENA
  нельзя прочитать из mbuf текущего DPDK data ENI, а аппаратной TX-метки ENA
  не предоставляет и в kernel-пути.
- Реальная следующая детализация DPDK выполняется диагностическими
  программными метками на локальных часах: получение слота sender-ом, конец
  сборки mbuf, вход и выход `rte_eth_tx_burst`; возврат `rte_eth_rx_burst`,
  конец разбора Ethernet/IP/UDP, конец разбора wire-пачки и публикация в
  SPSC. Это отделит стоимость нашего кода на обеих машинах. Остаток между
  выходом TX и возвратом RX по-прежнему совместно содержит ENA/Nitro/VPC и
  межхостовую погрешность; отдельный kernel-ENA опыт с аппаратной RX-меткой
  может служить только соседней диагностикой, но не разложением того же
  DPDK-тракта.

### Поправка: что считается Claude baseline

- Единственная корректная линейка Claude для наших сравнений — их неизменённый
  код, который мы сами запускаем на тех же AWS-узлах, в той же топологии и с
  той же схемой измерения, что и наше решение. Опубликованные Claude цифры с
  одного хоста, их оценки предельной скорости и прочие результаты из чужой
  конфигурации могут объяснять устройство решения, но не являются нашим
  численным baseline.
- Поэтому вывод выше о сравнении нашего `N=3` с опубликованным Claude `N=3`,
  включая оценку выигрыша по пропускной способности, отзывается. Проверка
  локальных сохранённых результатов показывает только Claude-запуски
  `N=1`: во всех их `manifest.json` указано `receivers: 1`. Сопоставимой
  Claude-планки `N=3` на нашем стенде в сохранённых данных сейчас нет.
- Следствие для плана: `N=1` сравниваем с уже снятой доверенной линейкой, а
  прежде чем делать выводы о целевом `N=3`, один раз прогоняем тот же
  неизменённый Claude-пакет через наш стенд с тремя физическими получателями.
  Это небольшое расширение существующего сценария запуска, а не новый
  baseline или отдельная система измерений.

### Claude `N=3` на нашем стенде и уточнение ENA-драйверов

- Существующий `scripts/claude-baseline.sh` расширен параметром
  `CLAUDE_BASELINE_RECEIVERS=1..3`. Исходники и deb Claude не меняются:
  sender получает три `--peer`, а тот же receiver/consumer из неизменённого
  пакета запускается по одному разу на каждом физическом receiver-узле. Для
  каждого узла отдельно сохраняются сырые CSV, summary и clock bracket.
- Сняты недостающие собственные baseline-точки:
  `claude-c86cc26ab2e8-r200000-n3-20260828T095225Z` и
  `claude-c86cc26ab2e8-r2000000-n3-20260828T095759Z`. В обоих случаях три
  повтора по `500k` измеряемых событий завершились на каждом получателе;
  primary clock correction равна нулю, максимальные PHC-границы составили
  `69.739` и `62.051` мкс.
- При `200k` Claude дал по трём узлам `p50 = 12.815/82.850/62.034` мкс и
  `p99.9 = 57.433/156.390/115.861` мкс. Соседний DPDK
  `fanout-dpdk-n3-20260828T093416Z` дал соответственно
  `12.459/80.884/57.119` и `21.700/96.378/75.835` мкс. Почти одинаковые
  межузловые сдвиги подтверждают, что большие различия абсолютной задержки
  между receiver-узлами в основном принадлежат шкалам часов. Небольшую разницу
  медиан победой не называем, а улучшение хвоста повторилось на всех узлах.
- При `2M` Claude дал `p50 = 15.312/83.700/456.865` мкс и
  `p99.9 = 133.776/300.010/607.966` мкс: третий последовательный получатель
  явно попал в накопление очереди. Сразу следующий DPDK
  `fanout-dpdk-n3-20260828T100347Z`, с окном `1200 нс` и целью пачки `3`,
  доставил общий диапазон без потерь и дал `p50 = 13.504/81.865/57.818` мкс,
  `p99.9 = 22.576/100.498/107.179` мкс. Source выдержал ровно `2M` событий/с,
  отправил `4.377M` пакетов за прогон при средней пачке `3.084`; все ENA
  allowance/error counters нулевые. Это сильный целевой результат `N=3`, но
  быстрые итерации и критерий стабильной победы по-прежнему проверяются
  соседними сериями `N=1`.
- Фактические слои data path перепроверены на source-узле. Control ENI работает
  через kernel `ena.ko` версии `2.17.2g`; data ENI `1d0f:ec20` привязан к
  `igb_uio`. Последний только отображает PCI/BAR в userspace и не является
  сетевым драйвером. Пакеты обрабатывает `net_ena` PMD из установленного
  DPDK `23.11.4` (ENA PMD `2.8.0`). Поэтому переход с `igb_uio` на
  `vfio-pci` сам по себе timestamp-ов не добавит; текущая схема соответствует
  [официальной инструкции AWS](https://github.com/amzn/amzn-drivers/blob/master/userspace/dpdk/README.md).
- Ограничение timestamp относится именно к нашей версии PMD, а не ко всем
  версиям ENA. В [DPDK 25.11](https://doc.dpdk.org/guides-25.11/rel_notes/release_25_11.html)
  ENA PMD `2.14` получил аппаратные RX timestamps с наносекундным разрешением:
  драйвер объявляет `RTE_ETH_RX_OFFLOAD_TIMESTAMP` только если устройство
  подтвердило возможность и кладёт метку в dynamic mbuf field. TX timestamp
  offload код по-прежнему не объявляет. Значит, короткая side-by-side проверка
  DPDK 25.11 может дать настоящую аппаратную границу на receiver и одновременно
  проверить новый PMD как вариант производительности, но не разложит весь
  участок от source TX до receiver RX.

### Явная уборка завершённых TX-пакетов

- В ENA PMD `2.8` уборка завершённых TX-дескрипторов выполняется внутри
  `rte_eth_tx_burst`, когда число свободных дескрипторов падает ниже
  `tx_free_thresh`. Для очереди `1024` значение по умолчанию равно `896`, то
  есть большой проход возникает примерно после каждых `128` занятых
  дескрипторов. Это подтверждено непосредственно
  [исходником DPDK 23.11](https://github.com/DPDK/dpdk/blob/v23.11/drivers/net/ena/ena_ethdev.c#L2926-L3008)
  и его [порогами ENA](https://github.com/DPDK/dpdk/blob/v23.11/drivers/net/ena/ena_ethdev.h#L43-L51).
- Проверен перенос этой работы в пустой оборот sender-а. Пакет
  `daba5e0bf6d0...` вызывал полную уборку после каждого пополнения резерва.
  Прогоны `fanout-dpdk-n1-20260828T102144Z` и
  `fanout-dpdk-n1-20260828T102319Z` при `200k` дали соответственно
  `p50/p99.9 = 9.840/17.546` и `10.869/18.248` мкс. Убрано почти по одному
  пакету на вызов; доставка полная, ошибки ENA нулевые.
- Чтобы не обходить TX-очередь на каждом событии, пакет `315ae2439ace...`
  прореживает явную уборку до одного раза на `32` пополнения. Прогоны
  `fanout-dpdk-n1-20260828T102711Z` и
  `fanout-dpdk-n1-20260828T102833Z` дали `14.037/19.757` и
  `10.866/17.906` мкс. Число вызовов уменьшилось до `28122`, каждый освобождал
  в среднем около `32` пакетов. Разброс абсолютной медианы между прогонами
  больше предполагаемого эффекта; устойчивого выигрыша над вариантом без
  явной уборки пока нет.
- При `2M` тот же вариант (`fanout-dpdk-n1-20260828T102954Z`) полностью
  доставил диапазон и дал `p50/p99.9 = 15.625/25.461` мкс при средней пачке
  `2.004`. Пустые обороты остаются: `52156` явных уборок освободили `2.244M`
  пакетов. Регрессии относительно рабочего диапазона прежней версии не видно,
  но улучшение также не доказано.
- Следующая связанная проверка — объявленный ENA режим
  `RTE_ETH_TX_OFFLOAD_MBUF_FAST_FREE`. Наш TX всегда использует прямые
  одно-сегментные mbuf из одного пула, поэтому выполняет его контракт; PMD при
  этом освобождает завершённые mbuf пачкой, а не по одному. Сначала проверяем
  его вместе с прореженной уборкой, затем при положительном результате отдельно
  убираем явную уборку, чтобы разделить эффекты.

### Пакетное освобождение mbuf и частота явной уборки

- Режим `RTE_ETH_TX_OFFLOAD_MBUF_FAST_FREE` подтверждён самим ENA PMD на обоих
  узлах. Без явной уборки прогоны `fanout-dpdk-n1-20260828T103901Z` и
  `fanout-dpdk-n1-20260828T104034Z` дали при `200k` соответственно
  `p50/p99.9 = 11.178/17.219` и `11.150/19.962` мкс. Доставка полная,
  ошибки и ограничения ENA нулевые. Результат остаётся внутри диапазона версии
  без этой настройки, поэтому выигрыш на редком потоке не доказан.
- Дополнительно проверен предложенный промежуточный интервал явной уборки: раз
  в `64` пополнения резерва, то есть примерно вдвое чаще штатного большого
  прохода ENA и вдвое реже предыдущего опыта `32`. Прогоны
  `fanout-dpdk-n1-20260828T104425Z` и
  `fanout-dpdk-n1-20260828T104546Z` дали `12.834/18.672` и
  `9.102/16.830` мкс. В каждом было около `14k` явных проходов, освободивших
  около `900k` mbuf, так что механизм действительно переносил работу, а не
  вызывался впустую. Во втором запуске DPDK принял один посторонний невалидный
  пакет, но весь измеряемый event-range доставлен без дыр и перестановок.
- Абсолютная медиана двух соседних неизменных запусков сдвинулась на `3.732`
  мкс, поэтому она непригодна для выбора такого малого эффекта. После вычитания
  медианы из каждого последовательного блока по `10k` событий получены
  медианные значения добавочного `p99.9`: `6.943` мкс для штатной уборки,
  `6.549` для интервала `32` и `6.755` для интервала `64`. Разница
  `0.2–0.4` мкс меньше разброса повторов; устойчивого улучшения нет.
- Явная уборка снова удалена из рабочего кода. `MBUF_FAST_FREE` пока оставлен
  как корректный дешёвый режим и проверяется на `2M`, где число завершений за
  единицу времени значительно выше; если там также нет эффекта, отдельной
  причиной считать его не будем.
- При `2M`, цели пачки `2` и окне `500 нс` fast-free запуск
  `fanout-dpdk-n1-20260828T105013Z` дал `p50/p99.9 = 13.921/24.670` мкс,
  среднюю пачку `2.019` и полную доставку. Сразу следующий запуск сохранённого
  пакета `e0a4a05376f6...` без fast-free,
  `fanout-dpdk-n1-20260828T105312Z`, дал `13.184/23.704` мкс и среднюю пачку
  `2.023`; ошибки и ограничения ENA также нулевые. Размах `p50..p99.9`
  практически одинаков (`10.749` против `10.520` мкс), устойчивого выигрыша
  fast-free нет.
- `RTE_ETH_TX_OFFLOAD_MBUF_FAST_FREE` удалён из рабочего кода вместе с явной
  уборкой. Оба опыта остаются отрицательными результатами: контракт выполнялся
  и механизмы реально работали, но ENA PMD уже достаточно амортизирует этот

  окно ожидания второго события `500 нс`), `200 нс` после receiver-а и

- Направление явной уборки закрыто: ENA PMD оставлен со штатной амортизацией.

### DPDK 25.11: новый PMD и аппаратная RX-метка

- Собран отдельный DPDK `25.11.3` только с нужным ENA PMD и `testpmd`; он
  устанавливается пакетом под `/usr/libexec/spectral-task/dpdk-25.11.3`, не
  подменяя системный DPDK. Первый развёрнутый пакет имел SHA256
  `a87c7a5668a23aa8d41ad8a5aedf197cec0af42f408ff4ff751c1f23e0beb5f9`.
  Функциональный `testpmd -> testpmd` на прежнем AWS epoch прошёл, а фактический
  ENA device объявил RX offload `TIMESTAMP`. DPDK 23.11 на том же устройстве
  эту возможность не объявлял.
- Чистые соседние прогоны DPDK 25.11 без аппаратных меток не показали
  самостоятельного ускорения или регрессии относительно 23.11. При `200k`
  `fanout-dpdk-n1-20260828T113131Z` дал `p50/p99.9 = 11.253/17.615` мкс
  против `11.308/17.396` мкс у 23.11. При `2M`
  `fanout-dpdk-n1-20260828T113251Z` дал `13.477/23.469` мкс против
  `13.184/23.704` мкс. Доставка полная, ENA errors/allowance нулевые. Поэтому
  переход нужен для диагностики, а не считается оптимизацией сам по себе.
- В DPDK receiver добавлен выключаемый флаг аппаратной RX-метки. Он
  регистрирует dynamic mbuf timestamp field, включает
  `RTE_ETH_RX_OFFLOAD_TIMESTAMP` только при подтверждённой возможности ENA и
  сохраняет метку рядом с программной. Обычный скоростной режим при выключенном
  флаге не меняется.
- Диагностический запуск `fanout-dpdk-n1-20260828T120735Z` при `200k` доказал
  реальную работу механизма: receiver сообщил `RX hardware timestamps=on`,
  доставил диапазон полностью и дал сквозные `p50/p99.9 = 9.330/18.566` мкс.
  Медиана от sender timestamp до аппаратного RX была `9.344` мкс. Попытка
  напрямую вычесть аппаратную PHC-метку из программной `CLOCK_REALTIME` дала
  медианно `-114 нс`: это не отрицательная обработка, а смешение двух близких,
  но не идентичных шкал часов.
- Stage-формат исправлен без увеличения SPSC slot: отдельно сохраняются
  software receive timestamp и необязательная hardware RX timestamp.
  `transport_to_receiver_ns` и `receiver_to_consumer_ns` теперь используют
  системные часы; отдельные поля показывают sender-to-hardware и
  hardware-to-software только как диагностические интервалы с явной оговоркой
  о clock domain. Unit/integration tests после изменения прошли; локальные
  latency-замеры не выполнялись.

### Подготовка локальной калибровки аппаратной RX-метки

- Receiver теперь при включённой аппаратной метке открывает локальный
  `/dev/ptp_ena`, до приёма трафика измеряет `CLOCK_REALTIME - ENA PHC` и
  переводит аппаратные метки в системную шкалу. Сначала используется ядерный
  `PTP_SYS_OFFSET_EXTENDED2`/`EXTENDED` с 25 тройками
  «системные до — PHC — системные после» и выбирается самая узкая скобка; если
  ioctl недоступен, остаётся 128 таких же измерений через `clock_gettime`.
  После потока калибровка повторяется, а receiver печатает начальную и конечную
  погрешность, дрейф offset и общий наблюдаемый бюджет ошибки.
- SPSC slot и wire protocol не увеличены: прежнее диагностическое поле теперь
  явно содержит уже переведённую в `CLOCK_REALTIME` аппаратную метку. Поэтому
  `hardware_to_software_receiver_ns` становится корректным локальным
  интервалом «аппаратный RX ENA → возврат из DPDK receive после разбора
  Ethernet/IP/UDP», а `receiver_to_consumer_ns` отдельно содержит разбор нашей
  дейтаграммы, публикацию в SPSC и handoff consumer-у.
- `summarize-fanout.py` научился читать stage CSV, проверять совпадение
  sequence range, строить всё распределение каждого этапа и прикладывать
  параметры PHC-калибровки из receiver log. На копии прежнего запуска с `500k`
  строк анализ завершился успешно; ожидаемо отметил старый прогон как не
  содержащий новой калибровки. Локальная C++-сборка, harness tests и transport
  test прошли; локальные performance-измерения не выполнялись, оставшихся
  процессов нет.
- Пока шла работа, общий TTL штатно остановил все пять EC2. Команда
  `aws-cluster-start` ошибочно поверила сохранённому Terraform output
  `running`, хотя AWS уже показывал `stopped`; тот же кластер пришлось поднять
  через recovery-ветку `cluster.sh up`. `cmd_start` исправлен: при активном в
  state, но фактически истёкшем стенде он теперь сверяет EC2/TTL через
  `cluster_lifecycle_state` и вызывает ту же идемпотентную recovery-ветку.
  Instance IDs не изменились, новый TTL вооружён, readiness снова пройден.

### Устранение дрейфа внутри диагностического прогона

- Для каждой калибровки receiver теперь сохраняет не только offset и ширину
  скобки, но и локальное `CLOCK_REALTIME` в её середине. Stage CSV дополнен
  абсолютной software-меткой receiver-а для каждого события; размер SPSC slot и
  рабочий путь без диагностики не менялись.
- Анализатор линейно интерполирует `CLOCK_REALTIME - PHC` между фактическими
  моментами калибровок. Он сдвигает соседние интервалы
  `transport → hardware RX` и `hardware RX → software RX` в противоположные
  стороны, поэтому их сумма и общий `transport → software RX` остаются
  неизменными. События за пределами скобки явно считаются отдельно, а старые
  артефакты без абсолютной software-метки остаются читаемыми без выдуманной
  коррекции.
- Локальная сборка, transport и harness tests прошли. Отдельный синтетический
  тест подтвердил знак и величину интерполяции: дрейф offset `-100 нс`
  преобразует исходные hardware-to-software `100/100/100 нс` в
  `100/150/200 нс`, сохраняя сумму двух соседних этапов.

  интерполяции и точная контейнерная сборка DPDK `25.11.3` прошли. Новый пакет

### Почему ENA PHC нельзя читать на каждой RX-выборке

- Диагностический запуск `fanout-dpdk-n1-20260828T143817Z` остановился во
  время прогрева: частый `clock_gettime(/dev/ptp_ena)` вернул `EBUSY` после
  `544237` событий. Измеряемая часть не началась, поэтому этот запуск не
  является результатом производительности и не смешивается с успешными.
- Это документированное аппаратное ограничение ENA, а не случайный сбой:
  официальный Linux ENA driver допускает не более `125` PHC get-time запросов
  в секунду и после превышения временно блокирует новые запросы. Точная версия
  ENA PMD в DPDK `25.11.3` также не заполняет `eth_dev_ops.read_clock` и не
  реализует timesync callbacks, поэтому общий `rte_eth_read_clock` не даёт
  отдельного быстрого пути к счётчику data ENI.
- Неудачный вариант с чтением PHC после каждой непустой RX-выборки удаляется,
  а не остаётся ещё одним рабочим режимом. Следующая реализация будет редко
  калибровать PHC относительно `CLOCK_REALTIME` на служебном ядре и строить
  кусочно-линейное преобразование между соседними точками. Это остаётся сильно
  ниже лимита устройства и не останавливает горячий receiver.

### Точная причина зависания периодического калибратора

- Первый короткий повтор сначала не дошёл до `READY`, потому что после отмены
  предыдущей SSM-команды остался старый receiver PID `63646`, удерживавший
  DPDK primary lock. Он был точечно остановлен; эта проблема относится к
  уборке после прерванного запуска, а не к трафику или PHC.
- После очистки пакет SHA256
  `232aaa03ab9818c3dde427c799080c695ddb42112f514ecbceb924cb7bc01b9d`
  с одиночным `clock_gettime(PHC)` воспроизвёл ожидание на короткой серии:
  consumer полностью получил `1M` прогревочных и `100k` измеряемых событий,
  а receiver успел напечатать `PHC periodic calibration stopping`, но не
  `stopped`.
- Снимок `/proc/74178/task/*/stack` снят до отмены. Главный поток спал в
  `futex_wait`, то есть ждал `join`; калибровочный поток был в обычном
  `hrtimer_nanosleep` на разрешённом CPU 0. Следовательно, PHC-вызов не
  зависал: рабочий поток продолжал повторять сон и не видел переданный через
  перемещённый `std::jthread` stop token.
- Исправление использует отдельный атомарный флаг завершения, который проверяет
  калибровочный поток. Scope guard выставляет его и присоединяет поток на любом
  выходе receiver-а; обычный путь также оставляет `request_stop` как второй
  сигнал. Следующий smoke-прогон должен подтвердить обе отметки остановки и
  финальную калибровку до возврата к полным сериям.

### Исправление диагноза: висячая ссылка на период сна

- Пакет SHA256
  `a7ee91e111139f64d42df41a789202f40dd1662c3a4866085998123d4c91dce9`
  с отдельным атомарным флагом снова полностью доставил короткую серию, затем

  scope guard оставлены как дополнительная защита всех выходов. Следующая
  короткая проверка должна подтвердить `stopping`, `stopped`, периодические и
  финальные точки калибровки; до неё исправление ещё не считается проверенным
  на AWS.

- Исходник ENA PMD `2.14.0` объясняет правдоподобный механизм: после обработки

  `rte_eth_rx_burst` на одной локальной шкале, без PHC/`CLOCK_REALTIME`, и
  только после неё значение `256` можно закреплять как рабочее.

  `5bec297dfc52fe2d80c1b3bd0091d2793e8e2fa083acee914fbc7f6c90985f69`

  межхостовая wire-метка остаётся `CLOCK_REALTIME`. Локальная и пакетная
  сборка прошли без предупреждений и ошибок, новый SHA подтверждён на всех
  четырёх прежних EC2 без их пересоздания.
- В профилированном запуске `fanout-dpdk-n1-20260828T164113Z` при `N=1`,
  `2M`, цели `2` и окне `500 нс` доставлены все `5M` событий. Доля прежнего

- Освобождённые циклы не означают такое же сокращение wall latency: sender
  сознательно остаётся в цикле до появления следующего события или истечения
  тех же `500 нс`. Поэтому CPU по-прежнему равен `100%`, а более дешёвая
  итерация прежде всего увеличивает частоту опроса очереди.

  `fanout-dpdk-n1-20260828T164443Z` с `500k` измеряемых событий дал для

  `570/1140/2230/17260 нс`. Медиана отличается лишь на `20 нс`, `p99` и

### Потеря полей как быстрая проба размера пакета: межзапускового A/B недостаточно

- Диагностический пакет SHA256
  `9437e0c5252a3b3beda802c43fa8e140a9ab982d01e2fb8dbc98e4fed2a54e6a`
  умеет вместо полного события передавать только `seq_id`, исходную метку
  времени, инструмент, тип и флаги. Рыночные поля намеренно теряются и на
  приёмнике заполняются нулями. Одиночный Ethernet-кадр уменьшается с
  `138/154/234` до `94` байт и целиком помещается в обычный `96`-байтный LLQ.
  Это только причинная проба, не кандидат в рабочий протокол.
- На прежних четырёх EC2 пакет установлен без их пересоздания. Четыре соседних
  запуска при `N=1`, `200k`, `400k` прогрева, `500k` измеряемых событий и без
  ожидания пачки полностью доставили диапазон без DPDK/ENA ошибок. Обычный,
  урезанный, обычный, урезанный режимы дали соответственно:

  | Режим | Run | p50 | p99.9 | clock uncertainty |
  |---|---|---:|---:|---:|
  | полный | `fanout-dpdk-n1-20260828T170814Z` | `62.381 мкс` | `86.333 мкс` | `53.399 мкс` |
  | урезанный | `fanout-dpdk-n1-20260828T170936Z` | `55.034 мкс` | `74.577 мкс` | `58.951 мкс` |
  | полный | `fanout-dpdk-n1-20260828T171103Z` | `61.821 мкс` | `78.807 мкс` | `55.972 мкс` |
  | урезанный | `fanout-dpdk-n1-20260828T171237Z` | `60.849 мкс` | `102.658 мкс` | `60.767 мкс` |

- Первый урезанный запуск выглядел лучше примерно на `7 мкс` по медиане, но
  второй воспроизвёл только `~1 мкс` и ухудшил хвост. Разность меньше границы
  межхостовых часов, поэтому этот A/B не доказывает ни выигрыш малого пакета,
  ни роль LLQ. Кроме того, он одновременно меняет объём нашей сериализации,
  число байт в кадре и число байт, которое ENA должна забирать из памяти.
- Следующий контроль сравнивает полный и урезанный кадр внутри одного запуска,
  а затем повторяет тот же смешанный поток с ENA `llq_policy=0`. Общая ошибка
  часов тогда сокращается внутри каждой пары. Эффект размера при отключённом
  LLQ оценивает копирование и меньший кадр; дополнительный эффект при обычном
  LLQ оценивает именно переход через его порог. После ответа диагностический
  код удаляется.

### Внутрисерийный контроль отделил примерно полмикросекунды LLQ

- Пакет SHA256
  `27ded773758ab84ea0f814f3ab8855894466f3cae6c486b95c2df32761236c8e`
  чередует полное и минимальное представление по схеме ABBA и принудительно
  ограничивает пробу одним событием на дейтаграмму. Поэтому `latency.csv`
  делится по `seq_id` на две одновременные серии по `500k` наблюдений: общая
  межхостовая ошибка часов одинакова для обеих и не попадает в их разность.
- В запуске `fanout-dpdk-n1-20260828T172121Z` с обычным LLQ `96` байт,
  `N=1`, `200k` и `1M` измеряемых событий минимальный кадр выиграл у полного:
  `730/794/594/642 нс` на `p50/p99/p99.9/p99.99`. Все `1.4M` событий вместе с
  прогревом дошли по одному в дейтаграмме без дыр, перестановок и ENA errors.
  Разделение по исходному типу показало почти одинаковый сдвиг `p50/p99`:
  `721/777 нс` для Trade `154 Б`, `710/804 нс` для BBO `138 Б` и
  `759/802 нс` для Book `234 Б`. Размер отброшенного хвоста различается сильно,
  а цена почти постоянна; это первая пороговая сигнатура LLQ, а не линейной
  цены байтов.
- Прямой контроль `llq_policy=0` на этом сочетании ENA/Nitro невозможен. В
  `fanout-dpdk-n1-20260828T172311Z` PMD явно сообщил об отключении LLQ, но ENA
  отверг создание TX submission queue (`Admin command 1 failed (6)`,
  `rte_eth_dev_start: Invalid argument`). Sender не перешёл к передаче, опыт
  остановлен, оставшихся процессов нет. Этот запуск не является latency-тестом.
- Вместо него тот же внутрисерийный поток повторён с широким LLQ `224` байта в
  `fanout-dpdk-n1-20260828T172812Z`. Тогда полные BBO/Trade тоже помещаются в
  LLQ, а Book `234 Б` всё ещё выходит за границу. Сдвиг минимального кадра на
  `p50/p99` стал `258/237 нс` для BBO и `276/255 нс` для Trade, но остался
  `799/805 нс` для Book. Разность разностей оценивает вклад полного помещения
  в LLQ примерно в `0.45–0.55 мкс`; оставшиеся примерно `0.25 мкс` объединяют
  меньшую нашу копию, разбор и число байт в тракте.
- На `p99.9` типовые разности не монотонны: обычный LLQ дал выигрыш минимального
  кадра `0.33/1.42/0.03 мкс` для Trade/BBO/Book, широкий —
  `1.60/1.12/-0.12 мкс`. Поэтому формат до `96` байт доказан как резерв для
  `p50/p99`, но не как улучшение целевого `p99.9`. Предыдущее решение не
  оставлять широкий LLQ сохраняется: он был только контрольной группой и
  уменьшает глубину TX-кольца.

### Коррекция следующего шага: широкий LLQ переоткрыт

- Последняя фраза предыдущего раздела была слишком сильной. Старые абсолютные
  A/B широкого LLQ действительно не показывали устойчивой победы, но новый
  внутрисерийный контроль дал новую причинную информацию: при переходе
  `96 → 224 Б` относительная цена полного BBO/Trade против общего минимального
  контроля сократилась на `0.45–0.55 мкс`, тогда как не поместившийся Book
  сохранил прежнюю цену. Это не доказывает итоговый абсолютный выигрыш режима:
  общий overhead и половинная глубина TX-очереди одинаково влияют на обе
  половины внутрисерийного потока и вычитаются. Но этого достаточно, чтобы
  переоткрыть широкий LLQ для настоящего полного формата.
- Цель `≤96 Б` больше не считается обязательной. На текущем формате BBO
  `138 Б` и Trade `154 Б` уже помещаются в широкий LLQ без потери данных, а
  Book `234 Б` превышает его лишь на `10 Б`. Сначала сравниваем обычный и
  широкий LLQ на реальном полном формате при `200k`, `2M` и обязательном
  fan-out. Только если половинная TX-очередь ухудшает хвост/предел нагрузки или
  lossless `≤96 Б` получается дёшево, проектируем более агрессивное сжатие.

### Проектирование следующего формата: это развитие, а не перенос Claude

- Проверка актуальных `message.h` и wire-кода подтвердила, что основной
  компактный формат Claude уже перенесён: `BBO/Trade/OrderBook = 64/80/160 Б`,
  используются числовой instrument, integer ticks/lots, временные дельты,
  смещения цен и накопительные итоги Trade. Следующая работа начинается поверх
  этой планки, а не повторяет её.
- Обнаружен особенно дешёвый кандидат для Wide LLQ: в полном стакане ровно
  `10 Б` полей `reserved` (`4 + 2 + 2 + 2`). Отдельное wire-представление без
  них даёт `160 → 150 Б` и полный Ethernet-кадр `234 → 224 Б`, не меняя ни
  одного полезного поля. Реализацию пока не начинали; сначала зафиксирован
  контракт и варианты в `docs/wire-format-size-hypotheses.md`.
- Простая замена абсолютного наносекундного timestamp или глобального sequence
  на `u32` отвергается арифметикой: время переполняется за `4.295 с`, а sequence
  при `200k/2M/8M` — за `5.97 ч / 35.79 мин / 8.95 мин`. Безопасные варианты —
  полная база на каждую дейтаграмму и короткие внутрипакетные дельты либо
  версионированная сессионная эпоха с явным rollover и восстановлением.

### Lossless `224 Б`: цена кодека устранена, порог Wide LLQ подтверждён

- Реализован самодостаточный lossless wire-кодек, который удаляет только поля
  `reserved`: `BBO/Trade/OrderBook = 60/76/150 Б`. После Ethernet, IPv4, UDP и
  32-байтного заголовка дейтаграммы одиночный стакан занимает ровно `224 Б`.
  Все полезные поля, включая исходные 64-битные `seq_id` и `send_ts_ns`,
  восстанавливаются; round-trip и предельный размер проверяются unit-тестом.
- Первая реализация в пакете SHA256
  `b3de7a3e197a8dd974448a011c2649ce69c7e8febe9042e19fdde08e1f10c70a`
  сначала кодировала событие во временный буфер, затем копировала его в mbuf,
  а на RX делала несколько обратных копий. Соседние Wide LLQ-прогоны
  `fanout-dpdk-n1-20260828T175121Z` (compact) и
  `fanout-dpdk-n1-20260828T175241Z` (full) при `N=1`, `200k` дали compact
  `p50/p99/p99.9 = 62.138/70.141/83.212 мкс` против
  `60.318/67.863/80.411 мкс`. Межхостовые границы `61.384/62.070 мкс` не
  позволяют объявить абсолютное ухудшение, но направление соответствовало
  очевидной лишней работе реализации.
- В пакете SHA256
  `aa62c43e4f825489459baa5cf04b81356818db60157868d5e7cd6b1b3316abf8`
  sender передаёт DPDK-прослойке сегменты прямо из SPSC без временного
  закодированного кадра, а receiver декодирует непосредственно в
  зарезервированный выходной слот. Смешанный ABBA-режим чередует full/compact
  по `seq_id` внутри одного запуска и принудительно отправляет одно событие на
  дейтаграмму. Поэтому общая ошибка часов вычитается из разности.
- В Wide LLQ-запуске `fanout-dpdk-n1-20260828T180209Z` все `1M` измеряемых
  событий доставлены без дыр, перестановок и ENA/DPDK errors. Разности
  compact минус full составили:

  | Тип | mean | p50 | p99 | p99.9 |
  |---|---:|---:|---:|---:|
  | BBO | `-6 нс` | `-1 нс` | `-89 нс` | `+192 нс` |
  | Trade | `+10 нс` | `+10 нс` | `+162 нс` | `-322 нс` |
  | Book | `-464 нс` | `-474 нс` | `-466 нс` | `-778 нс` |

  BBO и Trade уже помещались в широкий LLQ и показывают, что оставшаяся цена
  кодека находится около десятков наносекунд. Только уменьшившийся
  `234 → 224 Б` стакан получил устойчивые примерно полмикросекунды.
- Контроль с обычным LLQ в
  `fanout-dpdk-n1-20260828T180403Z`, куда не помещается ни один из полных или
  compact-кадров, также доставил все `1M` событий без ошибок. Для стакана
  compact минус full равен лишь `+10 нс mean`, `+78 нс p50`, `+43 нс p99` и
  `-1006 нс p99.9`. Разность Wide и ordinary эффектов даёт вклад порога LLQ
  примерно `0.47 мкс mean`, `0.55 мкс p50` и `0.51 мкс p99`; на `p99.9`
  одиночные хвостовые оценки пока нестабильны.
- Producer по условиям может сразу строить самодостаточное компактное событие в
  SPSC: он и сейчас конструирует C++-структуру прямо в зарезервированном слоте и
  последним действием ставит временную метку. Но текущий ABBA показал цену
  кодека лишь в десятки наносекунд. По явному решению ветка producer-builder и
  wire-ready SPSC закрыта: такой резерв не оправдывает смену ABI очереди и
  harness перед дедлайном. Пакетная база и внутридейтаграммные дельты в любом
  случае остаются у sender, потому что только он выбирает состав очередной
  дейтаграммы. Настоящая DPDK-owned память с владением до завершения ENA DMA
  остаётся отдельной zero-copy гипотезой, а не продолжением этой ветки.
- Рабочий compact-прогон `fanout-dpdk-n1-20260828T180754Z` при `N=1`, `2M`,
  Wide LLQ, цели пачки `2` и сроке `500 нс` доставил все `1M` измеряемых после
  `4M` прогрева без ошибок. Sender удержал `2M` событий/с, собрал `2 487 036`
  дейтаграмм из `5M` событий, средняя пачка `2.010`; сквозные
  `p50/p99/p99.9/p99.99 = 66.390/77.509/93.474/131.314 мкс` при clock
  uncertainty `58.605 мкс`. Это подтверждает функциональность под нагрузкой,
  но само по себе не сравнивает формат: большинство дейтаграмм содержит два
  события и всё равно превышает порог `224 Б`.
- Обязательный compact-прогон `fanout-dpdk-n3-20260828T181010Z` при `N=3`,
  `2M`, Wide LLQ, цели `3` и сроке `1200 нс` также удержал `2M` событий/с.
  Sender собрал `1 455 750` дейтаграмм из `4.5M` событий, средняя пачка
  `3.091`, и без ошибок отправил каждую трём адресатам; ENA allowance/error
  counters нулевые. Все три receiver получили измеряемый диапазон
  `4 000 001..4 500 000` без дыр, дублей и перестановок. Worst-receiver
  `p50/p99/p99.9/p99.99 = 64.357/71.731/86.563/107.730 мкс`, clock bounds
  `61.621..64.855 мкс`, поэтому абсолютный сдвиг относительно старого пакета
  не объявляется выигрышем без соседнего контроля.
- Третий receiver увидел `1` дополнительный невалидный DPDK-пакет сверх ровно
  `1 455 750` корректных дейтаграмм, отправленных и полученных каждым узлом.
  Он не относится к измеряемому sequence range и не повлиял на доставку, но
  сохраняется как наблюдение; повторение в соседнем прогоне потребует разбора.
- Соседний full-контроль `fanout-dpdk-n3-20260828T181223Z` и повтор compact
  `fanout-dpdk-n3-20260828T181454Z` образовали порядок compact/full/compact.
  Все три прогона корректно доставили диапазоны без потерь; одиночный invalid
  packet переместился на другой receiver в full-контроле и в повторе compact
  исчез, то есть не связан с wire-форматом.
- Full дал worst `p50/p99/p99.9 = 64.688/72.871/82.723 мкс`, два compact —
  `64.357/71.731/86.563` и `66.826/73.472/95.907 мкс`. Медиана и `p99` не
  показывают направленного сдвига, а короткий `p99.9` у compact выглядит хуже.
  Однако хвостовые `seq_id` почти не совпадают между тремя receiver: для top
  `0.1%` пересечение всех трёх равно `10/0/0` событий в compact/full/compact,
  попарные пересечения обычно `0..44` из `501`. Корреляции центрированных
  latency между receiver близки и одинаково малы (`0.07..0.15`) во всех трёх
  прогонах. Следовательно, выбросы рождаются после fan-out и не являются общей
  паузой sender/compact assembly; причинного ухудшения кодеком не установлено.
- Рабочий lossless-формат оставляем: его выигрыш для одиночного Book причинно
  подтверждён, а `2M/N=3` сохраняет пропускную способность и корректность.
  Короткие межзапусковые `p99.9` не используем как основание для новой ветки
  оптимизации без повторяемого общего источника выбросов.

### Первый свежий Claude `N=3` остановил старый диагностический gate

- Итоговый наш low-rate запуск `fanout-dpdk-n3-20260828T181749Z` использовал
  lossless compact, Wide LLQ, `N=3`, `200k` и не ждал наполнения пачки. Все
  `1M` измеряемых событий дошли каждому receiver без дыр, дублей и
  перестановок; worst `p50/p99/p99.9/p99.99 =
  61.716/68.383/81.266/142.796 мкс`, clock bounds `61.723..76.084 мкс`.
- Свежий неизменённый Claude `c86cc26` был запущен на тех же четырёх instance
  IDs, но после трёх измерительных повторов сценарий оборвался до сохранения
  summary: диагностическая двусторонняя UDP-проба receiver-1 получила
  uncertainty `204.596 мкс`, хотя обязательные ENA PHC bounds всех узлов были
  валидны (`23.195..29.072 мкс`). Это не неудача Claude и не latency-результат.
- В сценарии оставалась старая проверка, которая делала UDP uncertainty
  фатальной. Она противоречила уже принятой методике: UDP-проба не корректирует
  и не инвалидирует primary latency на общей ENA PHC-шкале. Проверка заменена
  предупреждением; полный baseline будет снят заново штатным путём.

### `200k/N=3`: устойчивое наше → Claude → наше преимущество

- Повторный неизменённый Claude `c86cc26` успешно сохранён как
  `claude-c86cc26ab2e8-r200000-n3-20260828T182528Z`. На каждом из трёх
  receiver объединены три повтора по `483 616` учитываемых событий; worst
  primary по медианам повторов равен
  `p50/p99/p99.9/p99.99 = 72.715/80.829/97.907/166.715 мкс`. ENA PHC
  uncertainty `56.988..60.876 мкс`; UDP-проба сохранена только как диагностика.
- Наши соседние lossless DPDK-запуски до и после Claude —
  `fanout-dpdk-n3-20260828T181749Z` и
  `fanout-dpdk-n3-20260828T183040Z`. Оба использовали те же instance IDs,
  `N=3`, `200k`, Wide LLQ и отсутствие ожидания пачки; каждый доставил всем
  ровно `1M` измеряемых событий без дыр, дублей и перестановок.
- Worst primary нашего первого/второго запуска:

  | Метрика | Наш до Claude | Claude | Наш после Claude |
  |---|---:|---:|---:|
  | p50 | `61.716 мкс` | `72.715 мкс` | `62.207 мкс` |
  | p99 | `68.383 мкс` | `80.829 мкс` | `68.188 мкс` |
  | p99.9 | `81.266 мкс` | `97.907 мкс` | `80.479 мкс` |
  | p99.99 | `142.796 мкс` | `166.715 мкс` | `138.314 мкс` |

- Два наших края совпадают в пределах `0.49 мкс p50`, `0.20 мкс p99` и
  `0.79 мкс p99.9`, а Claude между ними устойчиво хуже примерно на
  `10.5/12.5/17.0 мкс`. Практический результат воспроизводим и одинаково
  направлен по распределению. Формально разница меньше консервативных PHC
  bounds `~57..76 мкс`, поэтому отчёт не должен изображать её метрологически
  доказанным межхостовым наносекундным сдвигом; это сильный соседний A/B на
  неизменном EC2 epoch.

### `2M/N=3`: равный дальний хвост и неразрешимая абсолютная медиана

- Неизменённый Claude `c86cc26` сохранён как
  `claude-c86cc26ab2e8-r2000000-n3-20260828T183334Z`: по три повтора с
  `483 616` учитываемыми событиями на каждом receiver. Worst primary по
  медианам повторов равен `p50/p99/p99.9/p99.99 =
  55.669/62.203/81.516/305.436 мкс`; PHC bounds — `57.897..69.315 мкс`.

  устойчивой точкой.
- Сразу следом запущен наш lossless compact DPDK:
  `fanout-dpdk-n3-20260828T183955Z`, Wide LLQ, цель пачки `3`, срок

  абсолютные `p50/p99` текущая точность синхронизации ранжировать не позволяет.
  Это не свидетельство регрессии кода: доставка, темп и форма основной части
  распределения сохранились, а прежняя крупная победа над Claude при `2M/N=3`

- Соседняя серия Wide/ordinary/Wide состоит из
  `fanout-dpdk-n3-20260828T183955Z`,
  `fanout-dpdk-n3-20260828T184842Z` и

### Финальный Claude A/B обнаружил нестабильную постоянную очередь kernel UDP

- Неизменённый Claude был повторно установлен отдельным пакетом

- При `200k/N=3` Claude
  `claude-c86cc26ab2e8-r200000-n3-20260828T193844Z` дал worst
  `p50/p99/p99.9 = 118.531/123.206/133.473 мкс`; соседний наш
  `fanout-dpdk-n3-20260828T194451Z` — `60.958/67.013/79.429 мкс` и полную
  доставку. Наши low-rate запуски устойчиво остаются около
  `60–62/79–81 мкс`, тогда как прежний Claude был заметно лучше своего нового

  сохраняется, но новый разрыв `~54–58 мкс` нельзя переносить как стабильный
  размер эффекта.
- При `2M/N=3` Claude
  `claude-c86cc26ab2e8-r2000000-n3-20260828T194728Z` получил на receiver-1
  почти постоянные `min/p50/p99.9 = 338.610/341.243/357.224 мкс`, тогда как
  receiver-2/3 остались на `48.277/64.024` и `36.433/53.746 мкс` по
  `p50/p99.9`. Следующий наш `fanout-dpdk-n3-20260828T195319Z` не повторил

- Чтобы убрать минуты между соседними реализациями, в baseline-wrapper добавлен

  двунаправленную UDP-пробу; PHC snapshots, correction `0`, исходный Claude-код
  и три измерительных повтора остаются неизменны. Manifest явно сохраняет
  выбранный режим, а отсутствующие probe-поля записываются как `null`.

  `claude-c86cc26ab2e8-r2000000-n3-20260828T195857Z` всё равно сохранил

  201.128/204.100/207.755/228.402 мкс`. PHC uncertainty всех пар была
  `50.902..52.820 мкс`. Немедленный наш
  `fanout-dpdk-n3-20260828T200148Z` дал worst combined

  `63.607/72.079/86.034 мкс`. Доставка полная; один посторонний невалидный

- Полные chrony snapshots нашего запуска показывают фактический

  но не метрологически доказанная победа p50.
