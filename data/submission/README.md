# Данные сдаваемого отчёта

Этот каталог позволяет исполнить `analysis.ipynb` без доступа к AWS и без
многогигабайтного каталога `artifacts/`.

В корне лежит основной срез на стенде `precision-time → cluster`. Подкаталог
[`precision-time-only`](precision-time-only/README.md) содержит самостоятельный
срез более ранней согласованной EC2-эпохи без дочерней `cluster` placement group.
Notebook анализирует их одинаковыми методами, но не объединяет абсолютные
задержки и не вычитает одну эпоху из другой.

Файлы:

- `run-summary.csv` — 58 запусков одной EC2-эпохи: 48 запусков шести
  контрсбалансированных блоков сравнения с Claude для `N=1` и `N=3` и десять запусков на
  нагрузочный срез, срез по числу получателей и диагностический запуск с
  аппаратными RX-метками;
- `distribution-quantiles.csv` — плотные эмпирические квантильные кривые наших
  и Claude для `200k` и `2M` при `N=1` и `N=3`, симметрично уплотнённые в обоих хвостах;
- `fanout-distribution-quantiles.csv` — те же серии по каждому получателю, по
  времени доставки события всем получателям выбранного `N`, по равновзвешенному
  объединению получателей, среднему для события и разбросу между получателями;
- `comparison-blocks.csv` — исходные значения и парная разность
  `наш DPDK − Claude` для p50/p99/p99.9/p99.99 и ширины хвоста каждого из шести
  блоков, включая порядок плеч и расстояние между серединами запусков;
- `comparison-statistics.csv` — медиана и диапазон шести парных эффектов,
  точный двусторонний знаковый тест, собственный межблочный размах Claude и
  консервативный итог о разрешимости;
- `comparison-pooled-quantiles.csv` и
  `comparison-pooled-fanout-quantiles.csv` — описательные распределения после
  объединения всех шести блоков каждой реализации; статистический вывод из них
  не делается;
- `latency-density.csv` — сглаженные эмпирические плотности центральной части
  (`p1…p99`) отдельно для каждого блока;
- `comparison-pooled-density.csv` — два наложенных «колокола» после объединения
  шести блоков нашего решения и Claude для каждой пары `(N, частота)`;
- `latency-over-sequence.csv` — p99 и максимум превышения над собственным p50 в
  последовательных окнах по 1000 событий для поиска накопления очереди;
- `tail-bursts.csv` — число и длина непрерывных эпизодов дальше `p50 + 50 мкс`;
- `stage-breakdown.csv` — per-receiver разложение по доверенным программным
  границам, включая минимум, p50, p99 и p99.9. Аппаратные RX-интервалы исключены:
  PHC data ENI нельзя калибровать через PHC другого, control ENI;
- `provenance.json` — неизменённые manifest и summary исходных запусков,
  относительные пути к ним и правило агрегации.

Основная fan-out метрика строится по событиям, а не по уже готовым
перцентилям: строки выбранных получателей совмещаются по `seq_id`, для каждого
события берётся максимальная задержка, и только затем считается распределение.
Это реальное время, к которому событие доставлено всем получателям выбранного
`N`. Для `N=3` отдельно сохраняются кривые каждого получателя, равновзвешенное
объединение всех receiver-наблюдений, среднее `(L1 + L2 + L3) / 3` для каждого
события и разброс `max - min`.

Для Claude у каждого повторения сначала отбрасывается объявленный прогревочный
префикс. Разрешено отсечь только несовпадающие края записанных диапазонов;
внутренние `seq_id` обязаны быть непрерывными и одинаковыми. Оставшиеся
совмещённые повторения объединяются до расчёта перцентиля. Медиана перцентилей
отдельных повторений принципиально не используется: она скрывает редкие
задержки дальнего хвоста. `run-summary.csv` также содержит максимум готовых
per-receiver перцентилей как компактный диагностический агрегат.

Сырые per-event CSV сохраняются локально в `artifacts/aws-runner/`, который
исключён из Git. В репозиторий входят производные квантильные кривые, плотности,
сводные таблицы и `provenance.json`; этого набора достаточно для исполнения всех
ячеек notebook и проверки агрегации без многогигабайтного каталога измерений.

Сырая межхостовая задержка остаётся неизменной основной величиной. В
дополнительной центрированной шкале из задержек каждого получателя сначала
вычитается его собственный p50; это убирает постоянный сдвиг конкретной пары
часов и показывает форму хвоста, но не является поправкой к исходным данным.
Поэтому значения ниже p50 в центрированных производных данных отрицательны: это
отклонение от медианы, а не отрицательное время передачи. В сдаваемом notebook
такие графики обрезаны от p50 вправо, а полная левая половина сохраняется на
графиках положительной абсолютной задержки.

Кривые плотности строятся общей гистограммой сравниваемых реализаций с 320
интервалами и сглаживаются гауссовым ядром шириной два интервала. Это
эмпирический «колокол», а не подгонка нормального распределения: несколько пиков
и асимметрия данных не скрываются. Окно `p1…p99` нужно только для читаемости
центральной массы; оба дальних хвоста представлены квантильными кривыми.

Основная единица вывода — один контрсбалансированный блок: обе реализации
запускаются рядом, а порядок меняется `Claude → DPDK | DPDK → Claude`. Шесть
блоков дают шесть оценок разности. Объединённые кривые полезны для формы
распределения, но не заменяют эти парные эффекты и их межблочный разброс.

Каталог пересобирается только при наличии полных локальных AWS-артефактов:

```bash
uv run --frozen python scripts/build-submission-data.py \
  --suite artifacts/aws-runner/submission-suite-.../suite.json
```

Дополнительная эпоха пересобирается явно:

```bash
uv run --frozen python scripts/build-submission-data.py \
  --suite artifacts/aws-runner/submission-suite-20260829T161712Z/suite.json \
  --epoch-profile precision-time-only \
  --output data/submission/precision-time-only
```

Если `--suite` не задан, генератор берёт последнюю локальную завершённую suite.
Он читает сырые per-event CSV, но не изменяет их и отвергает смешение instance
IDs, вложенной `precision-time → cluster` топологии, package SHA,
dirty-версию измеренного `.deb`, невалидные часы или
неожиданно нарушенную доставку. Две точки за проверенной рабочей границей
допускаются только при явном `expected_saturation=true`: PPS-контроль
`4 млн/с, цель 3` и найденное насыщение полосы `5 млн/с, авто`. Поле `runner_dirty`
описывает состояние checkout измерительной оркестрации, а не исходники уже
собранного content-addressed пакета; оба признака сохраняются раздельно.
Абсолютные задержки из разных созданий EC2 нельзя сравнивать как A/B; исходные
instance IDs сохранены именно для проверки этого ограничения.
