# Данные сдаваемого отчёта

Этот каталог позволяет исполнить `analysis.ipynb` без доступа к AWS и без
многогигабайтного каталога `artifacts/`.

В корне лежит основной срез на стенде `precision-time → cluster`. Подкаталог
[`precision-time-only`](precision-time-only/README.md) содержит самостоятельный
срез отдельной EC2-эпохи без дочерней `cluster` placement group. Под эпохой
понимается серия на одном неизменном наборе instance IDs. Notebook применяет к
обоим срезам одинаковые методы и показывает их абсолютные задержки в отдельных
разделах.

Файлы:

- `run-summary.csv` — 58 запусков одной EC2-эпохи: 48 запусков шести
  контрсбалансированных блоков сравнения с Claude для `N=1` и `N=3` и десять запусков на
  нагрузочный срез, срез по числу получателей и диагностический запуск с
  аппаратными RX-метками;
- `distribution-quantiles.csv` — плотные эмпирические квантильные кривые наших
  и Claude для `200k` и `2M` при `N=1` и `N=3`, симметрично уплотнённые в обоих хвостах;
- `fanout-distribution-quantiles.csv` — те же серии по каждому получателю, по
  времени доставки события всем получателям выбранного `N`, по равновзвешенному
  объединению получателей, среднему для события и разбросу между получателями;
- `comparison-blocks.csv` — исходные значения и парная разность
  `наш DPDK − Claude` для p50/p99/p99.9/p99.99 и ширины хвоста каждого из шести
  блоков, включая порядок плеч и расстояние между серединами запусков;
- `comparison-statistics.csv` — медиана и диапазон шести парных эффектов,
  точный двусторонний знаковый тест, собственный межблочный размах Claude и
  консервативный итог о разрешимости;
- `comparison-pooled-quantiles.csv` и
  `comparison-pooled-fanout-quantiles.csv` — описательные распределения после
  объединения всех шести блоков каждой реализации; статистический вывод из них
  не делается;
- `latency-density.csv` — сглаженные эмпирические плотности центральной части
  (`p1…p99`) отдельно для каждого блока;
- `comparison-pooled-density.csv` — два наложенных «колокола» после объединения
  шести блоков нашего решения и Claude для каждой пары `(N, частота)`;
- `latency-over-sequence.csv` — p99 и максимум превышения над собственным p50 в
  последовательных окнах по 1000 событий для поиска накопления очереди;
- `tail-bursts.csv` — число и длина непрерывных эпизодов дальше `p50 + 50 мкс`;
- `stage-breakdown.csv` — разложение по получателям и доверенным программным
  границам, включая минимум, p50, p99 и p99.9. Аппаратные RX-метки data ENI
  хранятся в отдельной шкале без доступной калибровки к системным часам;
- `provenance.json` — неизменённые manifest и summary исходных запусков,
  относительные пути к ним и правило агрегации.

Основная fan-out метрика строится непосредственно по событиям: строки выбранных
получателей совмещаются по `seq_id`, для каждого события берётся максимальная
задержка, затем по полученному ряду считается распределение.
Полученный ряд представляет задержку до доставки события всем выбранным
получателям. Для `N=3` отдельно сохраняются кривые каждого получателя,
равновзвешенное объединение всех наблюдений получателей, среднее
`(L1 + L2 + L3) / 3` для каждого события и разброс `max - min`.

Для Claude у каждого повторения сначала отбрасывается объявленный прогревочный
префикс. Разрешено отсечь только несовпадающие края записанных диапазонов;
внутренние `seq_id` обязаны быть непрерывными и одинаковыми. Оставшиеся
совмещённые повторения объединяются до расчёта перцентиля, поэтому каждое редкое
хвостовое наблюдение сохраняет свой вес. `run-summary.csv` также содержит
максимум готовых перцентилей получателей как компактный диагностический агрегат.

Исходные CSV по событиям сохраняются локально в `artifacts/aws-runner/`, который
исключён из Git. В репозиторий входят производные квантильные кривые, плотности,
сводные таблицы и `provenance.json`; этого набора достаточно для исполнения всех
ячеек отчёта и проверки формул над производными таблицами. Полная пересборка
цепочки `исходные CSV → производные данные` требует локального каталога исходных
измерений.

Основная величина - исходная межхостовая задержка. Дополнительная центрированная
шкала вычитает собственный p50 каждого получателя и показывает форму хвоста
относительно медианы конкретной пары часов. Отрицательные значения в этой шкале
означают наблюдения левее медианы. Центрированные графики в отчёте начинаются
от p50, а полное распределение показано на графиках положительной абсолютной
задержки.

Кривые плотности строятся общей гистограммой сравниваемых реализаций с 320
интервалами и сглаживаются гауссовым ядром шириной два интервала. Они показывают
центральную массу, включая несколько пиков и асимметрию. Окно `p1…p99` сохраняет
читаемый масштаб центра, а дальние хвосты представлены квантильными кривыми.

Основная единица статистического вывода - один контрсбалансированный блок: обе
реализации запускаются рядом, а порядок меняется
`Claude → DPDK | DPDK → Claude`. Шесть блоков дают шесть оценок разности.
Объединённые кривые описывают форму распределения; парные эффекты и их
межблочный разброс служат основанием для сравнения реализаций.

Каталог пересобирается только при наличии полных локальных AWS-артефактов:

```bash
uv run --frozen python scripts/build-submission-data.py \
  --suite artifacts/aws-runner/submission-suite-.../suite.json
```

Дополнительная эпоха пересобирается явно:

```bash
uv run --frozen python scripts/build-submission-data.py \
  --suite artifacts/aws-runner/submission-suite-20260829T161712Z/suite.json \
  --epoch-profile precision-time-only \
  --output data/submission/precision-time-only
```

Если `--suite` не задан, генератор берёт последнюю локальную завершённую серию.
Он проверяет единый набор instance IDs, вложенную топологию
`precision-time → cluster`, SHA пакета, чистоту исполняемых входов, часы и
доставку. Набор также содержит два явно помеченных диагностических прогона
насыщения: PPS-контроль `4 млн/с, цель 3` и границу полосы
`5 млн/с, авто`; у обоих `expected_saturation=true`. Поле `runner_dirty`
описывает рабочую копию измерительной оркестрации; признак `source_dirty`
отдельно относится к входам сборки пакета с отпечатком в имени. Instance IDs
связывают каждое парное A/B с одной EC2-эпохой.
